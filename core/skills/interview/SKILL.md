# Interview

사용자와 무엇을 해야 하는지 합의하라. 질문 수보다 중요한 미결정 사항과 숨은 가정을 해소하는 것을 완료 기준으로 삼아라.

## 진입과 책임

- 사용자가 요청한 결과와 범위 안에서 인터뷰하라. 질문이나 추천으로 범위를 넓히거나 사용자의 결정을 대신 확정하지 말라.
- 단독 요청에서는 인터뷰와 합의 내용 정리까지만 수행하라. 백로그 ID나 Git 저장소를 요구하지 않고, 백로그 생성·브랜치·ADR·구현·커밋을 자동 실행하지 말라.
- `start-work`에서 진입하면 전달받은 요청, 백로그, 저장소 근거와 기존 합의를 재사용하라. 인터뷰 결과를 반환하고, 실행 계획 통합과 최종 시작 승인은 `start-work`에 맡겨라. 인터뷰 종료 승인과 구현 시작 승인을 중복해서 묻지 말라.
- `finish-work`에서 진입하면 질문·후속 검증·결정 변경 추적 방식을 재사용하고, 항목별 처분과 최종 반영·완료 승인은 `finish-work`의 절차를 따르라. 작업 시작 인터뷰를 처음부터 반복하거나 별도 인터뷰 종료 승인을 요구하지 말라.
- 인터뷰 중에는 읽기 전용 조사와 채팅만 사용하라. 별도 문서 저장이나 정책 문서 작성은 사용자가 그 작업을 요청하거나 승인했을 때 해당 절차로 수행하라.
- 질문, 선택지와 확인 요청은 일반 채팅으로 작성하고 답변을 기다려라. 질문용 다이얼로그·팝업 도구를 사용하지 말라.

## 1. 근거 수집과 의도 확인

질문 전에 현재 요청과 대화를 읽고, 저장소가 있다면 대상 루트와 변경 경로의 `AGENTS.md`, 관련 코드·테스트·문서를 필요한 범위에서 조사하라. 루트 지침이 없으면 코드, ADR, 빌드 파일과 관례를 근거로 삼되 레포 규칙을 만들어내지 말라. `CLAUDE.md`를 공통 정본으로 가정하지 말고 명시적으로 연결된 경우에만 보조로 읽어라.

확인한 내용을 다음처럼 구분하라. 사용자에게 매번 전체 분류표를 보여 줄 필요는 없다.

- **확인한 사실:** 코드·문서·사용자 발언에서 직접 확인한 내용과 출처.
- **추정:** 아직 확인되지 않은 해석과 그것이 틀렸을 때 달라지는 결과.
- **사용자 결정:** 목표, 허용할 동작, 범위와 트레이드오프처럼 사람이 선택해야 하는 내용.

코드로 알아낼 수 있는 사실은 조사하라. 기존 구현은 현재 동작의 근거이며 새 동작을 선택한 근거는 아니다. 코드·문서·사용자 설명이 충돌하면 어느 부분이 다른지 밝히고 기대 동작을 확인하라. 외부 사실이 필요하면 관련 공식 자료를 조사하고 사실과 추천을 구분하라.

해결하려는 문제, 기대 결과, 범위·비범위, 제약과 완료 기준을 짧게 재진술하여 사용자가 바로잡을 기회를 제공하라. 이미 명확한 내용을 질문으로 되풀이하지 말고, 빠졌거나 서로 모순되는 부분부터 확인하라.

## 2. 결정의 순서와 우선순위

관련 결정을 나열하고 어떤 결정이 다른 결정의 전제인지 파악하라. 기본 순서는 목적·성공 기준 → 범위·비범위 → 기대 동작 → 책임과 실패 처리 → 구현 제약·검증이다. 작업에 해당하지 않는 영역은 만들지 말라.

- 선행 결정이 끝난 주제 중 결과에 미치는 영향과 불확실성이 큰 것을 먼저 물어라.
- 아직 답하지 않은 결정의 답을 가정해야 하는 질문은 뒤로 미뤄라. 예를 들어 실시간 반영의 필요성이 미결정이면 메시지 처리 방식을 먼저 고르지 말라.
- 각 결정의 결론, 이유, 근거, 의존 관계와 위임 범위를 간결하게 유지하라. 긴 질문 목록을 사용자에게 한꺼번에 제시하지 말라.
- 한 주제를 깊게 다룬 뒤 다른 중요한 영역이 빠지지 않았는지 점검하라. 깊이 있는 후속 질문이 범위 전체의 누락을 가리지 않게 하라.
- 답변이 앞선 결정을 바꾸면 그 결정에 의존한 범위·설계·검증만 다시 확인하라. 영향을 받지 않는 합의는 유지하라.

## 3. 질문과 후속 검증

한 번에 하나의 결정 주제에 집중하라. 같은 결정을 이해하는 데 필요한 작은 질문 묶음은 허용하되 독립적인 주제를 섞지 말라.

결정 질문에는 왜 필요한지, 2~3개의 실제 선택지와 핵심 장단점, 추천안과 이유를 함께 제시하라. 사용자는 다른 답을 제시하거나 결정을 위임할 수 있다. 선택지가 하나뿐이면 억지 대안을 만들지 말고 제약을 설명하라. 의도가 아직 불명확하면 해결책 선택지를 먼저 제시하지 말고 목적이나 구체 사례부터 물어라.

중요한 답변에 미검증 가정이나 모호한 경계가 남으면 다음 중 실제 결과를 바꾸는 후속 질문으로 확인하라.

- **구체 사례:** 어떤 상황에서 무엇이 달라져야 하는가. 성공과 실패를 어떻게 구분하는가.
- **숨은 가정:** 이 선택이 성립하려면 어떤 전제나 의존성이 필요한가.
- **반례와 경계:** 예외·실패·부분 성공에서도 같은 결론인가. 무엇을 하지 않거나 거절할 것인가.
- **트레이드오프:** 충돌하는 목표 중 무엇을 우선하며 어느 비용까지 허용하는가.
- **용어와 원인:** 같은 단어를 다르게 쓰거나, 해결하려는 문제 대신 특정 해결책·증상만 설명하고 있지 않은가.

예를 들어 외부 변경 후 응답만 유실될 수 있는 작업에서 "실패하면 재시도"라는 답변은 충분하지 않다. 이미 성공했는지 판별할 근거와 재시도 시 중복 처리 여부를 확인하라.

핵심 결정의 가정과 경계가 실제 근거·사례로 검증됐는지 종료 전에 다시 살펴라. 기존 답변과 조사로 충분히 검증됐다면 형식적인 반론이나 추가 질문을 만들지 말라. 변수명 같은 가역적 세부사항은 합의된 위임 방침으로 처리하라.

## 4. 작업에 필요한 심화

`start-work`에서 진입했거나 기능 코드 변경의 설계를 인터뷰한다면 [작업 시작 전 시스템 검토](references/work-readiness.md)를 반드시 읽고 적용하라. 작은 변경도 관련성을 점검하고, 실제 위험 신호가 있는 관점만 심화하라. 기술과 무관한 단독 인터뷰에는 이 참조 문서를 강제하지 말라.

사람이 정해야 하는 비즈니스 규칙이 발견되면 정책 결정 문서가 필요한지 판정하라. 필요할 때만 근거와 함께 `decide-policy`를 제안하고, 사용자 승인 없이 문서를 만들지 말라. 같은 내용을 재인터뷰하지 않도록 합의한 규칙과 미결정 사항을 전달하고, 정책 결정 후 영향을 받는 인터뷰 결정에 반영하라.

## 5. 완료 조건

다음을 근거로 인터뷰 완료 여부를 판단하라.

- 목표, 범위·비범위, 제약과 검증 가능한 완료 기준이 명확하고 모순되지 않는다.
- 결과를 바꾸는 중요한 선택과 그 전제가 해결됐으며, 사용자 결정과 에이전트에게 위임한 세부사항을 구분할 수 있다.
- 핵심 결정의 숨은 가정·경계가 검토됐고, 선행 결정 변경의 영향이 반영됐다.
- 작업 시작용 심화가 적용되면 관련 시스템 근거와 불변식·실패 수렴·테스트 의무가 연결됐다.
- 남은 불확실성은 결과를 바꾸지 않는 위임 범위 안에 있다. 구현 결과를 바꾸는 미결정 사항을 단순한 잔여 위험으로 포장하지 않는다.

질문 횟수, 임의의 모호함 점수나 사용자 피로를 완료의 증거로 사용하지 말라. 위 조건이 충족되면 표현을 다듬거나 무관한 예외를 찾기 위해 질문을 늘리지 말라. 사용자가 중단하면 확정 내용과 남은 사항을 구분해 보고하고, 미완료 인터뷰를 완료로 표시하거나 실행으로 넘기지 말라.

## 6. 결과 전달과 재사용

채팅에 다음을 담은 간결한 브리프를 남겨라. 별도 인터뷰 파일을 기본 산출물로 만들지 말라.

- **의도와 기대 결과**
- **범위·비범위와 제약**
- **결정과 이유:** 중요한 선택, 검증한 가정·경계와 근거
- **위임된 결정:** 에이전트가 판단할 세부사항과 기본 방침
- **완료 기준:** 관찰하거나 검증할 수 있는 결과
- **시스템 근거:** 작업 시작용 심화를 적용한 경우 참조 문서의 근거 표
- **미결정 사항과 위험:** 완료를 막는 항목과 수용한 트레이드오프를 구분
- **인터뷰 완료 여부:** 완료 조건을 충족했는지와 부족한 근거

단독 인터뷰는 이 브리프에서 끝내고, 미해결 사항이나 사용자의 수정이 있으면 인터뷰를 이어가라. 내용에 대한 동의만으로 구현 시작 권한을 추정하지 말라. 이후 사용자가 작업 시작을 요청하면 `start-work`에 브리프를 전달하라.

`start-work` 안에서는 별도 종료 승인을 요청하지 말고 결과를 반환하라. `start-work`가 실행 계획을 포함한 최종 브리프로 시작 승인을 받는다. 이미 해당 범위의 최종 승인이 있으면 반복해서 묻지 않는다.

`finish-work` 안에서는 일반 작업 브리프 대신 해당 항목의 처분·근거·수정 방향·검증 의무·완료 판단에 대한 영향을 반환하라. 수정과 완료 실행은 `finish-work`의 최종 계획 승인을 따른다.

기존 합의 재사용 시 요청 범위와 관련 코드·제약이 여전히 같은지 확인하라. 달라진 부분과 빠진 근거만 보완하고, 유효한 답변은 다시 묻지 말라. 빠른 진행은 합의 재사용이며 필수 검토의 생략이 아니다.
