# Code Review

실제 변경과 주변 계약을 읽어 정확성, 회귀와 요구사항의 누락을 검수하라. RCA의 인과 추적을 사용하되, 리뷰 결과를 수정 명령이나 완료 승인으로 취급하지 말라.

## 책임과 경계

- 단독 리뷰는 결과 보고에서 끝낸다. 발견 사항의 처분 인터뷰, 소스 수정, 커밋과 백로그 이동은 `finish-work`가 담당한다. 사용자가 마무리를 요청하지 않으면 자동 진입하지 말라.
- 리뷰 중 추적 파일, 인덱스, HEAD와 브랜치를 변경하지 말라. 다른 리비전이나 파일 쓰기가 필요한 검증은 별도 임시 작업 공간에서 수행하라. GitHub 리뷰·댓글이나 별도 리뷰 문서를 자동 작성하지 말라.
- 모든 기능 변경은 기본 검수를 하되 실제 위험에 따라 심화 범위를 정하라. 오탈자나 생성물 동기화는 관련 검사로 충분하며, 스킬·규칙 변경은 동작 계약과 진입·승인·종료 시나리오를 검토하라.

## 1. 대상과 근거 고정

사용자 요청과 현재 대화에서 대상을 확정하라. 백로그 ID나 feature 브랜치 없이도 특정 커밋, 커밋 범위, 명시적으로 요청된 staged·unstaged·untracked 변경을 검토할 수 있다. `main` 작업이라고 리뷰를 생략하거나 빈 브랜치 diff를 정상 판정하지 말라.

- 커밋 리뷰는 기준·대상 리비전을 실제 SHA로 해석하고 커밋 목록과 누적 diff를 확인하라. 기준이 분명하지 않으면 질문하고, 임의로 `HEAD~1`을 전체 작업의 기준으로 삼지 말라.
- 코드·테스트·지침은 리뷰 대상 리비전의 내용을 기준으로 읽어라. 현재 작업 트리와 대상이 다르면 `git show`나 별도 임시 작업 공간을 사용하라. 다른 상태에서 실행한 검사를 대상 SHA의 검증 결과로 보고하지 말라.
- 미커밋 리뷰는 HEAD SHA, staged·unstaged 구분, 대상 파일과 diff를 식별하라. 재사용에 필요한 diff 해시와 untracked 파일의 내용 해시를 기록하라. 파일명이나 수정 시각만으로 같은 변경이라고 판단하지 말라.
- `BL-NNNN`이 연결됐다면 열린 항목과 완료 보관소에서 목표를 확인하라. 해당 작업의 기능 커밋에 같은 ID가 있는지 점검하되, 문서·스킬 등 백로그가 필수가 아닌 작업에 ID를 요구하지 말라. 다른 작업의 변경은 임의로 포함하지 말라.
- 루트와 변경 경로의 `AGENTS.md`, 관련 코드·테스트·문서, 확인 가능한 인터뷰·최종 브리프·ADR을 읽어라. 루트 지침이 없으면 기존 근거를 조사하되 레포 규칙을 만들어내지 말라. `CLAUDE.md`는 명시적으로 연결된 경우에만 보조로 사용하라.
- 합의나 외부 계약을 확인하지 못하면 근거 부족으로 구분하라. 독립 검토 가능한 범위는 계속 진행하되, 중요한 미확인 영역을 통과한 것으로 처리하지 말라.

## 2. 독립적인 관점과 검토 범위

구현자의 설명을 결론으로 받아들이지 말고 요구사항과 실제 코드를 각각 확인하라. 합의대로 구현했는지와 합의 자체가 놓친 것이 없는지를 따로 판단하라.

독립 리뷰어 사용이 허용되고 도구가 있다면 구현 맥락을 그대로 상속하지 않는 별도 리뷰어를 우선 사용하라. 승인된 목표·제약·중요 결정과 이유, 적용 지침, 정확한 변경 범위, 테스트 결과만 전달하라. 구현자의 긴 설명이나 "문제없음"이라는 결론을 검토의 전제로 전달하지 말라. 기본은 한 명이며, 여러 전문 리뷰어는 위험과 범위가 정당화하고 허용될 때만 사용한다. 같은 모델의 다수결을 정확성의 근거로 삼지 말라.

별도 리뷰어를 사용할 수 없으면 같은 에이전트가 독립된 검토 단계를 수행하고 맥락 분리의 한계를 보고하라. 어느 경우든 보고 전에 발견 사항의 근거를 재확인하라.

검토를 위임받은 리뷰어는 다시 리뷰어를 생성하지 말라. 지정된 범위를 직접 확인하고 결과를 요청자에게 반환하라.

[RCA와 다관점 검토](references/review-perspectives.md)를 읽고 관련 관점을 적용하라. 지정된 변경 전체를 확인하되 위험 신호가 없는 부분에 무관한 체크리스트를 적용하지 말라. 큰 변경은 기능·책임 단위로 나누고 빠진 범위를 기록하라.

## 3. 발견 사항 재검증

보고 후보마다 다음을 확인하라.

1. 발생 조건과 코드 경로를 구체화하고 사용자·시스템 영향을 연결한다. 특정 입력, 경합, 부분 실패에서만 발생해도 실제 가능한 조건이면 검토한다.
2. 호출자, 가드, 실제 어댑터·저장소 계약과 기존 테스트를 읽어 후보를 반증해 본다. 다른 계층의 방어로 문제가 성립하지 않으면 지적에서 제외한다.
3. 가능하고 필요한 로컬 테스트·정적 검사로 근거를 확인한다. 소스나 테스트를 직접 고치지 않고, 실행하지 못한 검증은 이유를 적는다.
4. 이번 변경이 만들거나 악화한 문제인지 구분한다. 기존 문제는 새 변경의 결함으로 섞지 않는다. 이번 완료 기준에 직접 영향을 주면 그 관계를 설명한다.
5. 같은 근본 원인의 중복 지적을 묶고, 단순 취향이나 막연한 리팩터링 제안은 완료 차단 결함으로 올리지 않는다.

테스트 파일 변경 여부와 무관하게 바뀐 동작의 검증을 확인하라. "테스트가 있음"에 그치지 말고 잘못된 동작이면 실제로 실패하는 단언인지, 대역만 보장하는 조건은 아닌지 살펴라. 테스트 추가 제안에는 잡아야 할 구체적인 실패를 연결하라. 무의미한 커버리지 목표를 만들지 말라.

심각도와 근거의 확실성을 분리하라. 영향이 크다는 이유만으로 추측을 확정 결함으로 승격하지 말라. 숫자로 된 자신감 점수를 증거 대신 사용하지 말라.

- **치명:** 데이터 손실, 보안 침해, 광범위한 장애처럼 즉시 차단해야 하는 문제
- **높음:** 핵심 기능 오류나 높은 회귀 가능성으로 완료 전에 수정해야 하는 문제
- **중간:** 특정 조건의 오동작 또는 실질적인 유지보수 위험
- **낮음:** 영향은 제한적이나 수정 가치가 분명한 문제

## 4. 설명을 포함한 전체 결과 보고

모든 발견 사항을 심각도 순으로 먼저 보고하라. 각 항목에 `R1`, `R2`처럼 이번 리뷰 안에서 안정적인 ID를 붙여 처분과 수정 결과를 연결할 수 있게 하라. 같은 항목을 재검증할 때 ID를 바꾸지 말라.

각 발견 사항은 다음 내용을 사용자가 이해할 수 있는 길이로 설명하라.

- **배경:** 해당 코드의 기능과 책임
- **발생 상황:** 문제가 나타나는 입력·순서·실패 조건
- **위치와 근거:** 좁은 파일·줄 위치, 확인한 사실과 아직 확인하지 못한 가정
- **인과 관계와 영향:** 원인 → 전파 → 사용자·시스템 결과, 기존 방어가 충분하지 않은 이유
- **완료 차단:** 예 / 아니오 / 판단 보류와 목표·완료 기준에 근거한 이유
- **권장 방향:** 해결 선택지의 핵심 차이, 비용·트레이드오프. 구현을 시작하지 않음

전체 보고에는 다음을 포함하라.

- **리뷰 대상:** SHA 또는 미커밋 변경 식별 정보, 범위, 연결된 백로그가 있으면 그 ID
- **발견 사항:** 위 설명을 포함한 전체 목록. 없으면 없다고 명확히 표시
- **커밋별 평가:** 커밋 범위를 검토한 경우 실제 문제나 중요한 판단만 간결하게 기록
- **게이트 판단:** 구현 준수와 인터뷰·요구사항 완전성을 각각 통과 / 실패 / 확인 부족으로 판정
- **검증 범위:** 실행한 검사와 결과, 검토한 관점, 미검토 영역과 중요한 근거 부족
- **최종 판단:** 완료 가능 / 수정 필요 / 판단 보류와 이유. 이는 기술 판단이며 실행·완료 승인이 아님

완료 차단 결함이 있으면 `수정 필요`, 알려진 차단 결함은 없지만 중요한 근거가 부족하거나 제품 판단이 필요하면 `판단 보류`, 관련 검토·검증이 충분하고 차단 항목이 없으면 `완료 가능`으로 판정하라. 지적이 없다는 사실만으로 통과시키지 말라. 반대로 문제 수를 채우려고 개선안을 만들어내지 말라.

리뷰 중 범위나 코드 상태가 바뀌었으면 확인한 범위를 밝히고 달라진 부분을 재검토하기 전까지 현재 상태 전체에 유효한 결과로 보고하지 말라. 단독 호출은 여기서 끝내고, `finish-work`에서 호출했다면 결과와 식별 정보를 반환하라.
