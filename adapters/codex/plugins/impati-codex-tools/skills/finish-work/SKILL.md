# Finish Work

리뷰 결과를 사용자가 이해하고 처분을 합의한 뒤 승인된 수정·검증·커밋·백로그 완료를 수행하라. 마무리 요청은 이 절차를 시작할 권한이며, 아직 제시하지 않은 수정이나 완료 계획의 승인으로 해석하지 말라.

## 1. 마무리 대상과 리뷰 확인

- 요청, 현재 대화, 작업 트리와 브랜치에서 목표, 완료 기준, 변경 범위와 기존 합의를 확인하라. 적용되는 루트·경로별 `AGENTS.md`와 로컬 검증·커밋·백로그 규칙을 읽어라.
- 중단된 마무리를 재개하면 실제 파일·백로그 위치·staged diff·커밋 로그를 인계 내용과 대조하라. 이미 적용한 수정, 생성한 후속 백로그와 완료 이동·커밋을 식별하고 남은 단계부터 진행하라. 기존 승인과 검증은 여전히 같은 범위·내용에 유효할 때만 재사용한다.
- 기능 코드 작업이면 연결된 `BL-NNNN` 항목을 읽어라. ID가 필요한데 없거나 범위가 불명확하면 사용자에게 확인하고 임의로 완료 항목을 만들지 말라. 문서·스킬 등 ID가 필수가 아닌 작업은 백로그 생성 없이 마무리할 수 있다.
- [code-review](../code-review/SKILL.md)를 읽고 유효한 리뷰가 없으면 수행하라. 이 스킬은 필수 의존이며 읽을 수 없으면 누락을 해결하기 전까지 완료 처리하지 말라.
- 기존 리뷰를 재사용하려면 기준·대상 SHA 또는 미커밋 diff·파일 내용 식별 정보, 완료 기준, 관련 코드·계약과 검증 결과가 현재 대상에 적용되는지 확인하라. 대화에 "리뷰 통과"만 남아 있으면 근거로 충분하지 않다.
- 달라진 부분은 diff와 영향받는 경로를 다시 검토하라. 변경 범위를 식별할 수 없거나 핵심 계약·설계가 바뀌어 이전 결과가 성립하지 않으면 해당 대상에 새 리뷰를 수행하라. 자동으로 반복 리뷰를 돌리는 대신 재검토 이유와 범위를 밝히라.
- 사용자 변경이나 다른 작업의 변경을 임의로 리뷰·수정·커밋에 포함하지 말라. 기능 코드 변경의 별도 구현 작업으로 확대되면 `start-work`로 범위를 다시 합의하라.

## 2. 전체 결과 공유와 항목별 인터뷰

처분 질문 전에 전체 리뷰 결과와 기술 판단을 먼저 공유하라. 이미 현재 대화에서 공유했다면 유효성 확인과 짧은 요약으로 충분하다. 중요한 근거 부족은 지적 없음과 구분하고, 조사 가능한 사실은 먼저 조사하라.

[interview](../interview/SKILL.md)를 읽고 사실·추정·사용자 결정 구분, 질문과 후속 검증, 결정 변경 추적을 재사용하라. 이 단계의 산출물은 아래 항목별 처분이며, 작업 시작 인터뷰나 승인된 범위 전체를 처음부터 반복하지 않는다. 수정이 새로운 시스템 결정을 만들면 관련 시스템 검토와 검증 의무도 갱신한다.

`interview` 의존 스킬을 읽을 수 없으면 경로와 배포 상태를 확인하고, 해결하기 전에는 처분 합의가 완료됐다고 간주하거나 수정으로 넘어가지 말라.

발견 사항을 심각도 순으로 하나씩 다뤄라. 각 항목의 배경, 발생 상황, 코드 근거, 원인에서 영향으로 이어지는 흐름과 완료 차단 여부를 짧게 다시 설명하라. 해결에 여러 방법이 있으면 실제 선택지 2~3개와 장단점·추천 이유를 제시하라. 관련 지적을 묶어 설명할 수 있지만 처분은 항목별로 확인한다.

사용자는 다음 중 하나를 선택할 수 있다.

- **반영:** 이번 범위에서 수정한다. 수정 방향과 검증할 결과를 합의한다.
- **보류:** 이번에는 수정하지 않는다. 이유, 남은 위험과 완료 가능 여부를 기록한다.
- **후속 백로그:** 독립 작업으로 분리한다. 지금 기록할 내용은 합의만 하고 최종 승인 뒤 `capture-backlog`로 생성한다.
- **기각:** 지적을 받아들이지 않는다. 근거상 오탐인지 실제 문제의 위험을 수용하는 것인지 구분한다.

오탐 기각은 코드·계약·검증 근거로 지적이 성립하지 않음을 확인하라. 위험 수용은 실제 문제를 없애지 않는다. 원래 완료 기준을 만족하지 못하면 보류·기각·후속 백로그라는 처분만으로 완료할 수 없다. 기준을 바꾸려면 원래 기준과 변경 기준, 사용자에게 미치는 영향과 남은 위험을 명시적으로 합의하라. 필수 레포 규칙이나 상위 제약도 확인한다.

사용자의 답변은 기록만 하고 다음 항목으로 넘어가라. 인터뷰 중에는 소스·테스트·백로그를 수정하거나 커밋하지 말라. 사용자가 앞선 결정을 바꾸면 의존하는 수정·검증·완료 판단을 다시 확인하라. 중단 시 확정 내용과 남은 항목을 보고하고 멈춰라.

발견 사항이 없으면 처분 질문을 만들지 말고 최종 계획으로 진행하라. 중요한 판단 보류 사항이 있다면 사실을 확인하거나 필요한 사용자 결정을 받아 해결하고, 해결되지 않으면 완료 계획을 승인받지 말라.

## 3. 최종 반영·완료 계획 승인

다음을 한 번에 정리하고 명시적인 승인을 받아라.

- 항목 ID별 처분, 반영할 수정 방향·범위, 보류·기각의 근거와 수용한 위험
- 후속 백로그로 기록할 내용과 원래 작업의 완료에 미치는 영향
- 변경된 완료 기준이 있다면 그 합의와 이유
- 수행할 표적 검증, 수정 diff·영향 경로 재검토와 관련 저장소 검증 명령
- 예상 커밋 경계·포함 파일과 백로그가 있으면 완료 이동 여부
- 검증과 최종 검수가 통과할 때 완료 이동·커밋까지 수행한다는 조건

발견 사항이 없으면 수정 계획을 만들지 말고 검증 근거와 완료 이동·커밋 계획만 승인받아라. 이미 같은 범위와 조건의 최종 승인을 받았다면 다시 묻지 않는다. 단순한 리뷰 결과 동의나 항목별 반영 선택은 최종 계획 승인과 구분하라.

승인 전에는 소스·테스트·백로그를 수정하거나 커밋하지 말라. 관련 없는 사용자 변경을 포함하지 않으며 push·PR·배포·플러그인 설치는 별도 요청 없이 수행하지 않는다.

## 4. 승인된 수정과 최종 검수

적용 전에 리뷰 대상, 브랜치, 작업 트리와 승인 범위가 그대로인지 확인하라. 달라졌으면 영향받는 결과와 계획을 갱신하고, 승인 범위가 바뀌면 다시 합의하라.

- `반영` 항목만 수정하고 승인된 후속 백로그만 생성하라. `capture-backlog`에는 `finish-work` 안의 생성임을 전달하고 파일 준비 후 반환하게 하라. 스테이징·커밋은 최종 검수 뒤 이 스킬이 담당한다. 보류·기각 항목은 수정하지 말라.
- 새로운 중요한 결정이나 별도 문제가 나타나면 영향을 받는 작업을 멈추고 인터뷰로 돌아가라. 추가 수정을 임의로 적용하지 말라.
- 표적 테스트와 관련 검증을 실행하고, 항목별 해결 근거를 연결하라. 실행하지 못한 검사를 통과로 보고하지 말라.
- 수정 전후 diff와 직접 영향을 받는 호출·데이터·실패 경로를 `code-review`의 기준으로 재검토하라. 테스트 통과만으로 최종 검수를 대체하지 말라.
- 검토한 최종 변경 상태를 다시 식별하라. 소스뿐 아니라 마무리 과정에서 바뀐 규칙·문서·생성물도 해당 범위에 맞게 확인하라. 이미 검토한 부분은 재사용하고 바뀐 부분과 영향 경로를 확인하라.
- 새 차단 문제가 생기면 완료를 보류하고 원인·범위·필요한 결정을 보고하라. 전체 리뷰를 무한 반복하거나 무관한 정리로 확대하지 말라.

과거 절차로 이미 `done`에 있는 백로그에서 차단 문제가 발견되면 최종 계획에 재개를 포함하고, 승인 후 수정 전에 열린 위치로 되돌려라. 차단 문제가 없으면 기존 위치를 유지한다.

## 5. 완료 판정·백로그 이동·커밋

발견 사항이 없거나 승인된 수정과 최종 검수가 통과했고, 중요한 근거 부족과 완료를 막는 미해결 항목이 없을 때만 완료할 수 있다. 명시적으로 재합의한 기준이 있으면 그 기준으로 판정하고 기존 기준에서 달라진 점과 수용한 위험을 보고하라.

- 최종 계획에 검증 통과 후 완료 이동·커밋까지 승인받았다면 같은 승인을 다시 묻지 말라. 새 위험·범위·조건 변경이 있으면 해당 변경을 합의한 뒤 진행하라.
- 대상 저장소의 백로그 관례를 우선하라. 기본 규약에서는 연결된 열린 항목을 내용 수정 없이 `docs/backlog/done`으로 이동한다. 완료 항목은 삭제하지 않는다. 백로그가 없는 문서·스킬 작업에는 이동이나 새 ID를 요구하지 않는다.
- 수정, 검증, 최종 검수, 완료 판정과 승인 확인, 백로그 이동, 스테이징·커밋 순서로 진행하라. 검증 실패·사용자 중단·완료 미승인 시에는 완료 이동이나 마무리 커밋을 하지 말고 남은 상태를 보고하라.
- 이동·스테이징·커밋마다 실제 결과를 확인하라. 완료 이동 후 커밋이 실패하면 이동한 파일과 사용자 변경을 보존하고 "완료 이동 반영, 커밋 미완료"로 보고하라. 자동 되돌리기나 새 백로그 생성을 하지 않으며, 승인된 커밋까지 확인되기 전에는 전체 마무리 성공으로 보고하지 말라. 커밋하지 않기로 합의한 작업은 파일 변경 결과로 보고한다.
- 실패·중단 뒤에는 성공한 단계의 경로·ID·해시와 남은 단계·원인을 채팅 인계에 남겨라. 커밋 결과가 불명확하면 로그와 diff로 반영 여부부터 확인하라. 원인이 해소된 뒤 현재 변경과 기존 검증·승인의 유효성을 확인하고 남은 단계만 재시도하라. 훅이 파일을 수정했다면 해당 diff와 검증·검수 범위를 갱신하고, 훅을 우회하거나 변경 없이 같은 실패를 반복하지 말라.
- 현재 작업의 파일이나 확인한 hunk만 스테이징하고 staged diff를 최종 확인하라. 기존 사용자 변경과 안전하게 분리할 수 없으면 질문하라. 이동 외의 새로운 변경이 섞였으면 검증·검수 범위를 갱신하라.
- 로컬 커밋 규칙을 따르고, 백로그 기반 기능 커밋은 같은 ID를 포함하라. 별도 규칙이 없으면 `<type>(bl-NNNN): <한국어 요약>`을 사용한다. 백로그가 필수가 아닌 작업은 ID 없는 로컬 컨벤션을 따른다.
- 각 커밋은 설명 가능한 의도로 나누고 구현과 이를 증명하는 테스트를 함께 두어라. 완료 이동은 마지막 관련 커밋에 포함한다. 수정이 없으면 완료 이동만 커밋하고, 커밋할 변경이 없으면 빈 커밋을 만들지 않는다.
- 사용자나 로컬 규칙이 커밋을 금지하면 커밋하지 말고 승인된 파일 변경 상태를 보고하라. 기존 커밋을 명시적 요청 없이 amend·rebase·squash하지 말라.
- 이 하네스 자체를 수정했다면 `CHANGELOG.md`도 갱신하되, 다른 프로젝트에는 그 프로젝트의 변경 기록 규칙을 적용하라.

## 6. 완료 보고

채팅에 검토한 최종 변경 상태, 항목별 처분과 실제 수정·검증 결과, 커밋 해시·메시지, 백로그 이동 여부와 이유, 후속 백로그 ID, 남은 위험·근거 부족·미커밋 변경을 간결하게 보고하라. 기술 검증 결과와 사용자가 수용한 위험을 구분하라. GitHub 리뷰나 별도 리뷰 결과 파일을 자동 작성하지 말라.
