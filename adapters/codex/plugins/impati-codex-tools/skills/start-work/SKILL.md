# Start Work

기능 코드 작업의 백로그 연결부터 구현·검증·커밋까지 관리하라. 모든 작업은 `interview`의 필수 검토와 완료 조건을 충족하고 최종 작업 브리프가 승인된 뒤 구현한다. 인터뷰만 요청받았다면 `interview`를 사용하고 이 실행 절차를 시작하지 말라.

## 1. 작업 컨텍스트 확인

대상 저장소 루트와 변경 경로의 `AGENTS.md`, 관련 코드·테스트·문서, 현재 브랜치와 작업 트리 상태를 읽기 전용으로 확인하라. 대상 프로젝트의 로컬 규칙을 우선하고, 조사 결과와 현재 대화의 합의를 `interview`에 전달하라. 조사로 알 수 있는 사실을 사용자에게 다시 묻지 말라.

구현 전에 검증 환경과 기준 상태도 짧게 확인하라.

- 관련 검증 명령, 필요한 런타임·도구·의존 서비스가 사용 가능한지 확인하고, 안전하게 실행할 수 있는 최소 관련 테스트를 실행하라. 매 작업마다 전체 테스트를 요구하지 말라.
- 확인한 리비전·작업 트리, 명령과 결과를 남겨 기존 실패, 환경 때문에 실행하지 못한 검사, 통과한 검사를 구분하라. 안전한 실행이 불가능하면 이유를 기록하라.
- 외부 시스템에 쓰는 검사나 승인 범위를 벗어난 설치·설정 변경을 진단 명목으로 수행하지 말라. 필요한 준비와 검증 공백은 실행 계획에 포함하고, 중요한 선택만 인터뷰로 확인하라. 환경 미비만으로 독립적으로 진행 가능한 조사까지 멈추지 말라.

## 2. 백로그 연결 확인

모든 기능 코드 작업을 하나의 `BL-NNNN` 백로그 항목과 연결하라.

- 사용자 요청, 현재 브랜치와 대화에서 백로그 ID를 확인하라.
- ID가 있으면 `docs/backlog/bl-NNNN-*.md` 항목을 읽고 배경과 목표를 인터뷰 컨텍스트로 사용하라. 열린 항목에 없으면 `docs/backlog/done/bl-NNNN-*.md`도 확인하라.
- 항목이 이미 `docs/backlog/done`에 있으면 완료된 작업이므로, 이어서 작업할지 새 백로그 항목을 만들지 사용자에게 확인하라. 같은 항목을 이어서 작업하기로 확정하면 최종 브리프 승인 후 구현 전에 열린 위치로 되돌려라.
- ID가 없으면 구현이나 브랜치 생성을 시작하지 말고 `capture-backlog`로 항목을 먼저 생성하라.
- 백로그 항목 생성 커밋이 안전한 기준 브랜치에 반영된 뒤 인터뷰를 계속하라.
- ID가 존재하지 않거나 여러 항목과 모호하게 일치하면 사용자에게 확인하라.
- 하나의 기능 코드 작업을 여러 백로그 ID에 임의로 연결하지 말라. 범위가 독립적이면 작업과 브랜치를 나눌지 사용자에게 물어라.

## 3. 필수 인터뷰 수행

[interview](../interview/SKILL.md)를 읽고 작업 시작용 인터뷰를 수행하라. 같은 플러그인에 함께 배포되는 필수 의존 스킬이며, 이름만 언급한 뒤 이 단계를 완료로 간주하지 말라.

- 사용자 요청, 백로그의 배경·목표, 저장소 조사 근거와 기존 합의를 전달하라. `interview`가 지정한 작업 시작 전 시스템 검토도 반드시 읽고 적용하라.
- 인터뷰가 반환한 결정·위임 범위·완료 기준·시스템 근거와 미결정 사항을 확인하라. 완료를 막는 항목이 있으면 해당 질문으로 돌아가고 최종 시작 승인을 요청하지 말라.
- 작은 변경이나 구체적인 요청도 필수 검토를 거친다. 실제 위험에 따라 질문과 심화 범위만 조절하라.
- 이미 유효한 인터뷰가 있으면 적용 가능성과 완료 조건을 확인하고 빠진 부분만 보완하라. 관련 코드나 범위가 바뀌면 영향을 받는 결정만 다시 검토하라.
- 의존 스킬을 읽을 수 없으면 경로와 배포 상태를 확인하라. 끝내 읽을 수 없으면 누락을 보고하고 구현으로 넘어가지 말라. 자체적인 축약 인터뷰로 대체하지 말라.
- 인터뷰 종료 승인을 별도로 받지 말라. 다음 단계에서 실행 계획을 합친 최종 브리프에 한 번만 시작 승인을 받는다.

## 4. 실행 계획 통합과 최종 승인

완료된 인터뷰 브리프의 의도, 범위·비범위, 결정과 이유, 위임 범위, 검증 가능한 완료 기준, 시스템 근거 표와 위험을 유지하라. 여기에 다음 실행 정보를 합쳐 하나의 최종 작업 브리프로 제시하라.

- **백로그:** `BL-NNNN` ID, 제목과 문서 경로
- **검증 계획:** 완료 기준과 인터뷰에서 확인한 불변식·실패 수렴의 테스트 의무를 수행할 방법과 명령, 사전 확인 결과·기존 실패·필요한 환경 준비와 실행하지 못하는 검사의 영향
- **커밋 계획:** 예상되는 논리적 리뷰 단위와 적용할 커밋 컨벤션
- **브랜치 계획:** 기준 브랜치와 사용할 브랜치. 로컬 규칙에 따른 예외도 반영
- **기록 계획:** 대상 프로젝트 규칙에 따른 ADR·문서화 필요 여부
- **위험과 승인 범위:** 위험하거나 되돌리기 어려운 변경을 명시하고 해당 변경에 대한 사용자 승인을 확인

실행 계획 때문에 새로운 중요한 선택이 생기면 인터뷰로 돌아가 영향을 받는 결정과 검증 의무를 갱신하라. 미결정 사항이 없는 최종 브리프로 작업을 시작해도 되는지 명시적으로 물어라. 이미 같은 범위의 최종 브리프가 승인됐다면 다시 승인받지 말라. 인터뷰 내용에 대한 동의만으로 실행 계획까지 승인됐다고 해석하지 말라. 승인 전에는 ADR이나 구현 파일을 작성하지 말라.

## 5. feature 브랜치 생성

최종 작업 브리프 승인 후 구현 전에 백로그 ID가 포함된 feature 브랜치를 준비하라.

승인된 브랜치 계획의 실행은 시작 승인에 포함된다. 같은 브랜치 생성을 별도로 승인받지 말라. 기준이나 사용할 브랜치를 바꿔야 하면 영향을 확인하고 변경된 계획만 합의하라.

- 대상 프로젝트의 로컬 브랜치 규칙을 우선하라.
- 별도 규칙이 없으면 `feature/bl-NNNN-kebab-case-title` 형식을 사용하라.
- 브랜치 제목은 백로그 파일 제목을 기반으로 짧게 작성하라.
- 브랜치를 만들기 전에 현재 브랜치, 기준 브랜치와 작업 트리 상태를 확인하라.
- 다른 작업의 변경이 있거나 안전한 기준 브랜치를 판단할 수 없으면 사용자에게 물어라.
- 같은 이름의 브랜치가 있으면 덮어쓰지 말고 기존 브랜치를 이어갈지 새 이름을 사용할지 확인하라.
- 이미 올바른 백로그 feature 브랜치에 있다면 새로 만들지 말고 계속 사용하라.
- 자동으로 push하지 말라.

## 6. ADR 기록

사용자가 최종 브리프를 승인하면 대상 프로젝트의 로컬 규칙에서 ADR을 요구하거나 허용하는지 확인하라. ADR을 사용하는 프로젝트에서는 구현 전에 `references/adr-convention.md`를 읽고 `docs/adr`에 ADR을 작성하라.

- 인터뷰에서 실제로 논의하고 승인한 내용만 기록하라.
- ADR을 진행 일지나 상세 구현 문서로 만들지 말라.
- 새 ADR 파일 자체는 승인된 작업의 첫 변경으로 간주하라.
- 저장소에 다른 ADR 규약이 있으면 더 가까운 저장소 규약을 우선하라.
- 대상 프로젝트가 ADR을 사용하지 않으면 최종 작업 브리프를 대화에 유지하고 ADR 작성 없이 구현으로 넘어가라.

## 7. 승인된 범위로 실행

필요한 ADR을 작성했거나 로컬 규칙에 따라 생략한 뒤 승인된 범위 안에서만 구현하라.

- 구현 중 새로운 중요한 결정이 나타나면 영향을 받는 작업을 멈추고 `interview`로 그 결정과 의존하는 범위·검증을 다시 확인하라.
- 새 결정이 승인되면 ADR을 사용하는 프로젝트에서는 같은 ADR의 `추가 결정`에 반영하라. ADR을 사용하지 않으면 대화의 최종 작업 브리프를 갱신한 뒤 계속하라.
- 단순한 가역적 세부 구현은 승인된 위임 방침에 따라 처리하라.
- 합의한 구현 완료 기준과 근거 표의 테스트 의무로 검증하라. 위험 작업의 관련 불변식이나 실패 수렴에 대응하는 자동 테스트가 빠졌으면 정상 흐름 테스트가 통과해도 완료로 보지 말라.
- 사전 검증과 비교하여 기존 실패와 새 회귀를 구분하라. 기존 실패라는 이유로 완료 기준 위반을 면제하거나 실행하지 못한 검사를 통과로 간주하지 말라. 검증 공백이 남으면 완료 판단에 미치는 영향을 보고하라.
- 검증을 통과해도 백로그 항목은 열린 위치에 유지하라. 사용자가 요청한 `finish-work`가 `code-review` 결과를 확인하고 필요한 인터뷰·수정·최종 검수를 거쳐 완료 판단과 `docs/backlog/done` 이동을 담당한다.
- 검증이 실패했거나 사용자가 작업을 중단해도 열린 상태를 유지하라.
- 대상 저장소에 다른 백로그 관례가 있으면 그 관례를 우선하고, `docs/backlog` 또는 `docs/backlog/done`을 임의로 만들지 말라.
- 이 하네스 저장소 자체의 작업이면 `CHANGELOG.md`도 갱신하라. 대상 프로젝트가 변경 기록을 관리하지 않으면 `CHANGELOG.md`를 새로 만들거나 갱신을 요구하지 말라.

## 8. 리뷰 단위로 커밋하고 보고

검증이 끝나면 현재 작업의 변경을 사용자가 커밋별로 리뷰할 수 있도록 정리하라.

### 커밋 경계 결정

- 하나의 커밋에는 하나의 설명 가능한 작업 의도를 담아라.
- 각 커밋이 가능한 한 독립적으로 이해되고 검증되며 되돌려질 수 있게 하라.
- 구현과 그 구현을 증명하는 테스트는 특별한 이유가 없으면 같은 커밋에 포함하라.
- 파일 종류만을 기준으로 기계적으로 나누지 말라. 분리하면 중간 커밋이 깨지거나 의미가 불완전해지는 변경은 함께 커밋하라.
- 서로 독립적인 기능, 수정, 리팩터링 또는 문서 변경은 별도 리뷰가 유용하면 나누어라.
- 커밋 수를 늘리는 것 자체를 목표로 삼지 말라. 작은 단일 의도의 작업은 하나의 커밋이면 충분하다.

### 안전하게 스테이징

- 커밋 전에 `git status`와 diff를 확인하라.
- 현재 작업에서 생성하거나 수정한 변경만 스테이징하라.
- 사용자가 만든 기존 변경이나 다른 작업의 변경을 임의로 포함하거나 되돌리지 말라.
- 같은 파일에 현재 작업과 기존 변경이 섞여 안전하게 분리할 수 없으면 사용자에게 물어라.
- 광범위한 자동 스테이징보다 명시적인 파일이나 검토한 hunk를 선택하라.
- 비밀, 인증 정보, 생성물 또는 로컬 전용 파일이 포함되지 않았는지 확인하라.

### 커밋 생성

- 대상 프로젝트의 로컬 커밋 규칙과 메시지 컨벤션을 우선하라.
- 모든 기능 코드 커밋에 현재 `BL-NNNN` 추적 ID를 포함하라.
- 별도 컨벤션이 없으면 `<type>(bl-NNNN): <한국어 요약>` 형식을 사용하라.
- `type`은 작업 의도에 맞춰 `feat`, `fix`, `refactor`, `test`, `docs`, `chore` 등에서 선택하라.
- 요약은 간결한 한국어로 작성하라.
- 각 커밋을 만들기 전에 staged diff가 해당 의도와 일치하는지 확인하라.
- 가능한 범위에서 각 커밋 단위의 관련 검증을 수행하라.
- 사용자가 커밋하지 말라고 했거나 로컬 규칙이 자동 커밋을 금지하면 커밋하지 말고 변경 상태를 보고하라.
- 명시적 요청 없이 기존 커밋을 amend, rebase, squash 또는 삭제하지 말라.
- push와 PR 생성은 별도 요청이 있을 때만 수행하라. 브랜치 생성은 승인된 브랜치 계획을 따른다.

### 완료 보고

생성한 순서대로 각 커밋을 보고하라.

- 짧은 커밋 해시와 메시지
- 해당 커밋의 작업 의도와 핵심 변경
- 수행한 검증과 결과
- 남아 있는 미커밋 변경과 그 이유
- 백로그 ID와 문서 경로
- 작업 브랜치 이름
- 구현 검증은 끝났지만 코드 리뷰 전이므로 백로그가 열린 상태라는 점

커밋이 하나여도 같은 형식으로 보고하라.

## 9. 다음 단계 안내

작업과 커밋 보고가 끝나면 `$code-review`로 검토만 받거나 `$finish-work`로 리뷰·반영 인터뷰·수정·완료 처리까지 진행할 수 있음을 한 문장으로 안내하라.

- 코드 리뷰를 자동 실행하지 말라.
- 사용자가 코드 리뷰 또는 작업 마무리를 요청했을 때 해당 스킬로 진행하라.
- 코드 리뷰만 통과해도 백로그는 열린 상태로 남는다. 완료 처리는 `finish-work`를 따른다.
- GitHub 리뷰, push 또는 PR 생성으로 확대하지 말라.

## 기존 합의 재사용

빠른 진행은 `interview`의 필수 검토를 생략하는 경로가 아니다. 기존 대화가 완료 조건을 충족하는지 확인해 유효한 답변을 재사용하고, 변경되거나 빠진 부분만 보완하라. 최종 승인도 현재 범위를 포함하면 재사용하되, 브랜치 준비와 필요한 기록 등 아직 수행하지 않은 실행 단계부터 이어가라.
