# Decide Policy

무엇이 참이어야 하는지를 사용자와 합의하고, 시점이 고정된 정책 결정 문서로 남겨라. 정책 문서는 구현 방향을 정하는 문서가 아니라 구현이 만족해야 할 인터페이스다.

## 기본 원칙

- 정책 문서는 "왜 이렇게 정했나, 무엇을 버렸나, 언제 다시 보나"를 담는다. 시점을 고정하고 뒤집을 때는 고치지 않고 새 번호를 딴다.
- "지금 유효한 규칙 전부"를 주장하는 카탈로그 문서를 만들지 말라. 코드가 바뀌는 순간 거짓이 되고 아무도 고치지 않는다.
- 지금 무엇이 참인지는 명세 테스트가 답한다. 문서는 결정을, 테스트는 현재 상태를 담당한다.
- 정책 문서는 필요할 때만 만든다. 산출물이 있어야 해서 만드는 문서는 비용만 남긴다.
- 정책을 확정하는 것과 구현 방식을 고르는 것을 섞지 말라. 구현 방식 결정은 ADR의 몫이다.
- 대상 프로젝트에 이미 정책 문서 관례가 있으면 그 관례를 우선하라.

## 1. 필요 여부 판정

문서를 쓰기 전에 지금 이 작업에 정책 결정 문서가 필요한지 먼저 판정하라. 판정 근거를 사용자에게 한두 문장으로 밝혀라.

다음 중 하나라도 해당하면 필요하다고 보라.

- 규칙이 코드에서 유도되지 않고 사람이 정해야 한다. 값이나 경계가 임의로 정해졌고 다르게 정할 수도 있었다.
- 규칙이 사용자 요청을 거절하거나 제한한다. 거절 기준은 나중에 반드시 다시 질문받는다.
- 규칙이 여러 모듈이나 팀에 걸쳐 있어 한 곳의 코드만 읽어서는 전모를 알 수 없다.
- 같은 규칙을 두고 이미 서로 다른 이해가 관찰됐다.
- 규칙을 뒤집으면 사용자에게 보이는 동작이 바뀐다.

다음에 해당하면 만들지 말라.

- 코드와 테스트만 읽어도 규칙과 이유가 분명하다.
- 기술적 제약이 규칙을 강제해서 다르게 정할 여지가 없었다.
- 이번 변경이 기존 정책의 구현 방식만 바꾼다. 이 경우는 ADR의 대상이다.
- 규칙이 아직 실험 중이고 곧 바뀔 예정이다.

필요하지 않다고 판정하면 문서를 만들지 말고 그 이유를 알린 뒤 원래 작업으로 돌아가라. 판단이 갈리면 사용자에게 필요 여부부터 물어라.

## 2. 기존 정책 확인

`docs/policy`의 기존 문서를 읽고 같은 주제의 결정이 이미 있는지 확인하라.

- 같은 주제의 유효한 문서가 있고 이번 결정이 그 안의 빈칸을 채우는 정도면 새 문서를 만들지 말고 기존 문서를 알려라.
- 기존 결정을 뒤집는다면 기존 문서를 수정하지 말고 새 문서를 만들어 대체 관계를 남겨라.
- 주제가 겹치지만 독립적으로 읽혀야 하면 새 문서로 만들고 관련 문서를 상호 참조하라.

## 3. 정책 인터뷰

한 번에 하나의 결정 주제에 집중하라. 저장소를 읽어 알 수 있는 사실은 질문하지 말라.

아래 항목 중 이 정책에 관련된 것을 빠짐없이 확인하라. 체크리스트를 기계적으로 전부 묻지 말라.

- 이 정책이 답해야 하는 질문과 정책이 없을 때 생기는 문제
- 이 정책이 성립시키려는 상태
- 확정할 규칙과 각 규칙의 근거
- 규칙이 거절하는 사용자 시나리오와 허용하는 시나리오, 특히 경계에 있는 사례
- 경계값, 단위, 대소문자와 공백 취급 같은 해석의 여지
- 규칙이 적용되는 범위와 적용되지 않는 범위
- 정책이 의도적으로 정하지 않고 구현에 위임하는 것
- 실제로 검토한 대안과 버리는 이유
- 이 정책을 다시 볼 조건

각 질문에는 가능하면 2~3개의 실제 선택지와 각 선택이 사용자 동작에 만드는 차이, 추천안과 추천 이유를 함께 제시하라. 사용자가 규칙을 확정하지 못하면 임의로 결정하지 말고 미결로 남길지 물어라.

정책과 구현 방식이 섞여 들어오면 분리하라. "무엇이 참이어야 하는가"만 이 문서에 담고, "그것을 어떤 방식으로 구현하는가"는 ADR이나 작업 브리프로 넘겨라.

## 4. 정책 문서 작성

인터뷰에서 합의한 내용을 확인받은 뒤 `references/policy-convention.md`를 읽고 그 규약대로 문서를 작성하라.

- 인터뷰에서 실제로 합의한 내용만 기록하라. 논의하지 않은 규칙을 채워 넣지 말라.
- 규칙은 검증 가능한 단언으로 쓰고 각 규칙에 규칙 ID를 부여하라.
- 구현 방법, 클래스 이름, 파일 경로, 진행 상황을 문서에 담지 말라.
- 미결로 남긴 사항은 결정한 것처럼 쓰지 말고 미결로 표시하라.

## 5. 커밋하고 보고

- 정책 문서 작성 자체는 기능 코드 변경이 아니므로 `BL-NNNN` 연결을 요구하지 말라. 진행 중인 코드 작업의 일부라면 그 작업의 커밋 규칙을 따르라.
- `git status`와 diff를 확인하고 이번 정책 문서만 스테이징하라. 기존 사용자 변경을 포함하지 말라.
- 로컬 커밋 규칙을 우선하고, 규칙이 없으면 `docs(pd-NNNN): <한국어 요약>` 형식을 사용하라.
- 저장소가 Git을 사용하지 않거나 사용자가 커밋하지 말라고 하면 파일만 만들고 상태를 보고하라.
- 완료 시 정책 ID, 파일 경로, 확정한 규칙 수, 미결로 남긴 사항, 커밋 해시와 메시지를 보고하라.
- push, 브랜치 생성, PR 생성은 별도 요청 없이 수행하지 말라.

## start-work와의 관계

- `start-work` 인터뷰 중 확정할 규칙이 사람이 정해야 하는 정책이라고 판단되면 이 스킬을 제안하라. 사용자가 승인할 때만 진입하고 자동으로 문서를 만들지 말라.
- 정책이 확정된 뒤 그 정책을 구현하는 코드 작업은 `start-work` 절차로 진행하라.
- 정책 문서는 무엇이 참이어야 하는지를, ADR은 그것을 어떤 방식으로 구현할지를 담는다. 하나의 정책을 여러 방식으로 구현할 수 있을 때만 ADR이 필요하다.
- 이미 이 대화에서 규칙, 근거, 대안과 재검토 조건이 합의됐다면 같은 질문을 반복하지 말고 확인만 받고 문서를 작성하라.
