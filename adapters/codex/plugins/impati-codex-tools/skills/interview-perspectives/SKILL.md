# Interview Perspectives

기존 인터뷰에 관점별 충족 기준과 상태 확인을 더하라. 질문 수나 점수 대신 관련 관점의 결정·근거·검증 방법이 갖춰졌는지 판단한다.

## 호출과 책임

- 사용자가 이 스킬 또는 "다관점 인터뷰"를 명시적으로 요청했을 때만 수행하라. 작업이 복잡하거나 위험하다는 이유로 자동 실행하지 말라. 일반 `interview`와 `start-work`의 기본 인터뷰는 그대로 유지한다.
- 먼저 [interview](../interview/SKILL.md)를 읽고 근거 수집, 사실·추정·사용자 결정의 구분, 질문 순서, 반례 검토, 완료 조건과 인계 절차를 적용하라. 이 스킬은 그 절차에 관점별 상태를 추가하며 별도의 인터뷰를 두 번 수행하지 않는다. 기능 코드 설계라면 기본 인터뷰가 요구하는 시스템 검토도 읽어라.
- 기본 스킬·필수 참조를 읽을 수 없으면 누락을 해결하기 전까지 완료로 판단하지 말라. 임의의 축약 절차로 대체하지 않는다.
- 단독 호출은 읽기 전용 조사와 채팅 브리프에서 끝난다. 구현·백로그·문서 파일·커밋을 생성하지 말라. `start-work`나 `finish-work` 중 명시적으로 요청됐다면 해당 범위의 인터뷰를 보완하고 호출한 절차에 반환하라. 실행 승인이나 인터뷰 종료 승인을 추가하지 않는다.
- 여기서 "확인됨"은 요구와 결정의 근거가 명확하다는 뜻이다. 구현 검증, 성능 측정 또는 보안 감사가 통과했다는 뜻으로 보고하지 말라.

## 1. 관점과 근거 확인

[관점별 충족 기준](references/perspectives.md)을 읽고 모든 관점의 관련성을 짧게 점검하라. 사용자 요청·관련 코드·레포 규칙으로 판단하며, 관련 있는 관점만 심화한다. 자료가 없어 판단하지 못한 관점을 `해당 없음`으로 처리하지 말라.

초기에 이번 작업의 관련 관점과 중요한 공백을 짧게 공유하라. 관점 목록을 질문 목록으로 읽어 주지 말고, 먼저 조사할 사실과 사용자에게 물을 결정을 구분하라. 이미 유효한 인터뷰가 있으면 결정과 근거를 관점에 대응시키고 빈 부분만 보완한다. 참조에 없는 도메인 특유 관점은 누락 시 결과가 달라지는 이유와 충족 기준을 붙여 추가할 수 있다.

관점별로 현재 상태, 그 근거와 남은 결정, 완료 차단 여부를 유지하라.

| 상태 | 판단 기준 |
| --- | --- |
| 확인됨 | 관련 요구·책임·경계가 합의됐거나 유효한 근거로 확인됐으며, 중요한 결과를 검증할 방법이 있다. 구현의 실제 검증은 별도로 남겨 둔다. |
| 결정 필요 | 기대 동작·범위·트레이드오프 등 사람이 정해야 할 선택이 남았다. 무엇이 달라지는지 명시한다. |
| 근거 부족 | 현재 동작·제약·의존 계약을 뒷받침할 자료가 없거나 충돌한다. 조사할 근거와 판단에 미치는 영향을 명시한다. |
| 해당 없음 | 이번 범위에 영향이 없다는 근거가 있다. 이유를 짧게 남긴다. |

하나의 관점에 미결정과 근거 부족이 함께 있으면 선행 장애를 상태로 표시하고 나머지도 남겨라. 표의 상태를 바꾸기 위해 근거 없는 가정이나 사용자 결정을 만들어내지 말라.

## 2. 중요한 공백부터 인터뷰

- 기본 인터뷰의 결정 의존 순서를 유지하라. 선행 결정이 갖춰진 항목 중 결과에 미치는 영향과 불확실성이 큰 것을 먼저 다룬다. 모든 관점에 똑같은 질문 수를 할당하지 않는다.
- 관점의 이름보다 구체 상황과 결과를 질문하라. 예를 들어 "데이터 파기를 고려했나요?" 대신 "탈퇴한 계정이 백업 복원 뒤 다시 나타나면 어떤 상태여야 하나요?"처럼 결정이 필요한 경계를 드러내라.
- 코드로 확인할 사실은 먼저 조사하고, 기존 합의·위임으로 해결되는 내용은 재질문하지 말라. 조사 불가능한 사실은 어떤 근거가 필요한지 밝히며 사실 확인을 사용자 취향 선택으로 대체하지 않는다.
- 질문 방식과 대안 설명은 기본 인터뷰를 따른다. 한 번에 하나의 결정 주제에 집중하고 채팅 답변을 기다려라. 관점별 별도 승인이나 질문용 팝업을 추가하지 말라.
- 답변 뒤에는 관련 관점과 의존하는 관점을 함께 갱신하라. 예를 들어 보관 기간 변경은 파기·백업·비용·감사 기록에, 비동기 전환은 사용자 완료 표시·재시도·관측에 영향을 줄 수 있다.
- 중요한 답변은 구체 사례와 반례로 확인하라. 보류나 후속 작업이라는 이름만으로 현재 목표를 막는 공백을 해소하지 말라. 새로운 기능이나 전면 재설계를 목록 충족을 위해 추가하지 않는다.

## 3. 종료 판정과 전달

기본 인터뷰의 완료 조건과 함께 다음을 확인하라.

- 모든 관점의 관련성이 검토됐고, 관련 관점의 판단에 근거가 있다.
- 구현 결과를 바꾸는 중요한 `결정 필요`·`근거 부족`이 남아 있지 않다. 하나라도 남으면 다른 관점의 충족으로 상쇄하지 말고 미완료로 보고하라.
- 관점 사이의 충돌과 선행 결정 변경의 영향이 해결됐다. 중요하지 않은 잔여 사항은 기본 인터뷰가 허용하는 위임 범위 안에서만 남긴다.
- 합의한 불변식·품질 제약·실패 처리에 대응하는 검증 방법이 있다. 아직 수행하지 않은 검사와 조사로 확인한 근거를 구분한다.

기본 인터뷰 브리프에 다음 표를 합쳐 채팅으로 전달하라. 시스템 검토 근거 표와 중복되는 내용은 같은 근거를 참조하고 재작성하지 말라.

| 관점 | 상태 | 근거·합의 또는 남은 공백 | 검증 방법·완료 차단 여부 |
| --- | --- | --- | --- |

관련 관점은 각각 표시하고 해당 없는 관점은 이유가 같으면 묶어도 된다. 각 답변마다 전체 표를 반복하지 말고, 종료·중단 시 전체 상태와 미결정 사항을 알 수 있게 남겨라. 질문 횟수나 평균 점수로 종료하지 말라. 충분히 확인되면 형식적인 추가 질문 없이 끝내고, 중단되면 미완료 상태와 다음 확인 사항을 인계하라.
