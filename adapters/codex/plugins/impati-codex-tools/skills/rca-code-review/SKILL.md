# RCA Code Review

백로그 기반 코드 변경을 커밋별·누적 관점에서 검토하고 결과를 채팅으로만 보고하라. Root Cause Analysis의 인과 추적을 적용해 표면적인 증상뿐 아니라 원인, 영향 전파와 재발 가능성을 확인하라.

리뷰 중에는 소스 파일을 수정하거나 커밋, 브랜치, 백로그, GitHub 리뷰 또는 별도 결과 문서를 만들지 말라.

## 1. 리뷰 대상 확정

다음을 읽기 전용으로 확인하라.

- 사용자 요청에 포함된 `BL-NNNN`
- `docs/backlog/bl-NNNN-*.md` 또는 `docs/backlog/done/bl-NNNN-*.md`의 배경과 목표
- 현재 브랜치와 기준 브랜치
- 기준 브랜치 이후의 커밋 목록과 각 diff
- 누적 브랜치 diff
- 적용되는 `AGENTS.md`, 로컬 리뷰 규칙과 검증 명령

백로그 ID, 기준 브랜치 또는 리뷰 범위가 불명확하면 추측하지 말고 사용자에게 물어라. 사용자가 요청하지 않은 uncommitted 변경이나 다른 백로그 커밋을 리뷰 범위에 포함하지 말라.

각 기능 코드 커밋이 동일한 `BL-NNNN`을 포함하는지 확인하고, 다른 ID나 추적되지 않은 변경이 섞여 있으면 범위 문제로 보고하라.

## 2. 인과 관계 재구성

코드를 평가하기 전에 작업의 인과 관계를 재구성하라.

### 버그 또는 장애 수정

다음 연결을 확인하라.

```text
관찰된 증상 → 발생 조건 → 직접 원인 → 근본 원인 → 수정 지점 → 기대 결과
```

- 수정이 증상을 가리는 데 그치지 않고 근본 원인을 해결하는가
- 근본 원인에 대한 가정이 코드와 증거로 뒷받침되는가
- 같은 원인이 다른 경로에 남아 있는가

### 기능 또는 구조 변경

다음 연결을 확인하라.

```text
백로그 목표 → 핵심 가정 → 변경된 상태·흐름 → 영향받는 소비자 → 실패 가능성
```

- 구현이 백로그 목표와 직접 연결되는가
- 암묵적 가정이 유효한가
- 정상 경로뿐 아니라 상태 전이와 실패 경로가 일관적인가

## 3. 커밋별 리뷰

각 커밋을 생성 순서대로 독립 검토하라.

- 커밋 메시지와 실제 변경 의도가 일치하는가
- 한 커밋이 독립적으로 이해되고 가능한 범위에서 검증·되돌리기 가능한가
- 필요한 구현과 테스트가 함께 있는가
- 이후 커밋이 없으면 깨지는 불완전한 중간 상태를 만들지 않는가
- 백로그 범위를 벗어난 변경이나 우연한 정리가 섞이지 않았는가

커밋 분리 자체가 결함을 만들지 않았다면 단순한 취향 차이는 지적하지 말라.

## 4. 누적 다관점 리뷰

전체 브랜치 결과를 다음 관점에서 검토하라. 작업과 관련 없는 관점은 억지로 채우지 말라.

### 의도와 범위

- 백로그의 배경과 목표를 충족하는가
- 명시적 비범위나 요청하지 않은 변경을 침범하지 않았는가

### 정확성과 근본 원인

- 핵심 로직과 상태 전이가 모든 관련 경로에서 올바른가
- 수정 지점이 근본 원인과 일치하는가
- 예외, 경계값, 부분 실패와 복구가 빠지지 않았는가

### 영향 전파와 회귀

- 호출자, 소비자, 데이터와 외부 인터페이스에 미치는 영향이 안전한가
- 호환성, 마이그레이션 또는 롤백 문제가 없는가
- 인접 기능에서 예상하지 못한 동작 변화가 생기지 않는가

### 재발 방지와 검증

- 테스트가 구현 세부사항이 아니라 원인과 불변 조건을 검증하는가
- 같은 결함이 다른 경로에서 재발할 가능성이 남아 있지 않은가
- 관측 가능성이나 실패 진단에 필요한 정보가 충분한가

### 설계와 유지보수

- 책임, 추상화와 모듈 경계가 작업 의도에 맞는가
- 불필요한 결합, 중복 또는 변경 확산을 만들지 않았는가
- 미래 변경에서 같은 문제를 반복하기 쉬운 구조가 아닌가

### 상황별 위험

관련 있을 때만 보안, 개인정보, 성능, 동시성, 트랜잭션, 자원 정리와 운영 위험을 검토하라.

## 5. 증거와 검증

- 발견 사항은 구체적인 파일과 가능한 한 좁은 줄 위치를 근거로 제시하라.
- 사실, 코드에서 도출한 추론과 확인하지 못한 가정을 구분하라.
- 재현 또는 검증에 도움이 되는 로컬 테스트·정적 검사 명령을 실행할 수 있다.
- 리뷰를 위해 소스나 테스트를 수정하지 말라.
- 근거 없는 가능성이나 일반적인 스타일 선호를 결함처럼 보고하지 말라.
- 발견 사항이 없으면 없다고 명확히 말하고 남은 테스트 공백이나 확인하지 못한 위험만 적어라.

심각도는 다음 기준을 사용하라.

- **치명:** 데이터 손실, 보안 침해, 광범위한 장애처럼 즉시 차단해야 하는 문제
- **높음:** 핵심 기능 오류나 높은 회귀 가능성으로 병합 전에 수정해야 하는 문제
- **중간:** 특정 조건에서 오동작하거나 유지보수 위험을 실질적으로 높이는 문제
- **낮음:** 영향은 제한적이지만 수정 가치가 분명한 문제

## 6. 채팅 보고

발견 사항을 심각도 순으로 먼저 보고하라. 장황한 과정 설명보다 리뷰 결론과 증거를 우선하라.

```text
리뷰 대상
- 백로그: BL-NNNN 제목
- 브랜치: feature/bl-NNNN-title
- 기준 브랜치: main
- 커밋: N개

발견 사항
[높음] 짧은 제목
- 위치: path/to/File.ext:line
- 관찰: 코드에서 확인한 사실
- 인과 관계: 원인 → 전파 → 결과
- 영향: 사용자 또는 시스템에 미치는 문제
- 권장 조치: 수정 방향

커밋별 평가
- abc1234 feat(bl-NNNN): 한국어 요약 — 평가

검증과 남은 위험
- 실행한 검사와 결과
- 확인하지 못한 영역

최종 판단
- 승인 가능 / 수정 후 재검토 / 사용자 결정 필요
```

파일이나 GitHub에 리뷰 결과를 작성하지 말고 채팅 응답으로만 제공하라.

## 7. 후속 작업 안내

발견 사항을 다음처럼 구분하라.

- 현재 백로그 목표 달성에 필요한 수정은 현재 작업의 차단 사항으로 보고하라.
- 현재 범위 밖이지만 나중에 해결할 가치가 있는 별도 문제는 후속 작업 후보로 분리하라.

후속 작업 후보가 있으면 원할 경우 `$capture-backlog`로 배경과 목표를 기록할 수 있음을 안내하라. 사용자의 명시적 요청 없이 백로그 파일을 만들거나 구현을 시작하지 말라.
