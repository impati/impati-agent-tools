# RCA Code Review

백로그 기반 코드 변경을 커밋별·누적 관점에서 검토하고 결과를 채팅으로 보고하라. Root Cause Analysis의 인과 추적을 적용해 표면적인 증상뿐 아니라 원인, 영향 전파와 재발 가능성을 확인하라. 전체 리뷰 후 발견 사항을 하나씩 인터뷰하고, 모든 결정에 대한 최종 승인을 받은 뒤 승인된 변경만 일괄 반영하라.

리뷰와 항목별 인터뷰 중에는 소스 파일을 수정하거나 커밋, 브랜치, 백로그, GitHub 리뷰 또는 별도 결과 문서를 만들지 말라. 반영 계획의 최종 승인 후에만 적용 단계로 전환할 수 있다. 리뷰 결과는 계속 채팅에만 남긴다.

## 1. 리뷰 대상 확정

다음을 읽기 전용으로 확인하라.

- 사용자 요청에 포함된 `BL-NNNN`
- `docs/backlog/bl-NNNN-*.md` 또는 `docs/backlog/done/bl-NNNN-*.md`의 배경과 목표
- 현재 브랜치와 기준 브랜치
- 기준 브랜치 이후의 커밋 목록과 각 diff
- 누적 브랜치 diff
- 대상 저장소 루트와 변경 경로에 적용되는 `AGENTS.md`, 로컬 리뷰 규칙과 검증 명령
- 확인 가능한 `start-work` 최종 브리프나 ADR의 영향 경계, 불변식, 실패 수렴과 테스트 의무

백로그 ID, 기준 브랜치 또는 리뷰 범위가 불명확하면 추측하지 말고 사용자에게 물어라. 사용자가 요청하지 않은 uncommitted 변경이나 다른 백로그 커밋을 리뷰 범위에 포함하지 말라.

루트 `AGENTS.md`가 없어도 오류로 취급하지 않는다. 그 경우 코드, ADR, 빌드 파일과 기존 관례에서 기술 기준을 조사하되 레포 고유 기준을 만들어내지 말라. 인터뷰 산출물이 현재 대화나 저장소에 남아 있지 않으면 확인하지 못한 근거로 구분하고, 구현과 백로그만으로 독립 검토할 수 있는 범위를 계속 진행하라.

각 기능 코드 커밋이 동일한 `BL-NNNN`을 포함하는지 확인하고, 다른 ID나 추적되지 않은 변경이 섞여 있으면 범위 문제로 보고하라.

## 2. 인과 관계 재구성

코드를 평가하기 전에 작업의 인과 관계를 재구성하라.

### 버그 또는 장애 수정

다음 연결을 확인하라.

```text
관찰된 증상 → 발생 조건 → 직접 원인 → 근본 원인 → 수정 지점 → 기대 결과
```

- 수정이 증상을 가리는 데 그치지 않고 근본 원인을 해결하는가
- 근본 원인에 대한 가정이 코드와 증거로 뒷받침되는가
- 같은 원인이 다른 경로에 남아 있는가

### 기능 또는 구조 변경

다음 연결을 확인하라.

```text
백로그 목표 → 핵심 가정 → 변경된 상태·흐름 → 영향받는 소비자 → 실패 가능성
```

- 구현이 백로그 목표와 직접 연결되는가
- 암묵적 가정이 유효한가
- 정상 경로뿐 아니라 상태 전이와 실패 경로가 일관적인가

## 3. 커밋별 리뷰

각 커밋을 생성 순서대로 독립 검토하라.

- 커밋 메시지와 실제 변경 의도가 일치하는가
- 한 커밋이 독립적으로 이해되고 가능한 범위에서 검증·되돌리기 가능한가
- 필요한 구현과 테스트가 함께 있는가
- 이후 커밋이 없으면 깨지는 불완전한 중간 상태를 만들지 않는가
- 백로그 범위를 벗어난 변경이나 우연한 정리가 섞이지 않았는가

커밋 분리 자체가 결함을 만들지 않았다면 단순한 취향 차이는 지적하지 말라.

## 4. 누적 다관점 리뷰

전체 브랜치 결과를 다음 두 게이트로 독립 검토하라. 첫 게이트가 통과해도 둘째 게이트를 생략하지 말고, 인터뷰 문구를 그대로 재확인하는 데 그치지 말라.

### 구현 준수 게이트

- 구현이 인터뷰에서 확정한 정책, 책임 경계, 핵심 불변식과 실패 수렴을 지키는가
- 근거 표의 각 테스트 의무가 실제 자동 테스트에 대응하고 현실적인 실패 조건을 재현하는가
- 레포 지침과 승인된 범위·비범위·검증 명령을 지키는가

### 인터뷰 완전성 게이트

- 커밋과 누적 diff에서 새로 드러난 호출·데이터 경계를 따라갔을 때 빠진 상태 소유자나 쓰기 권한이 없는가
- 성공, 실패, 결과 불명, 중단 후 재개에서 책임 주체와 수렴 근거가 정해져 있는가
- 중복, 순서 역전, 동시 실행, 재시도, 부분 성공과 데이터 불일치 중 실제 가능한 실패 모드가 누락되지 않았는가
- 대역·어댑터·하위 시스템이 보장하는 계약과 애플리케이션 책임의 경계가 실제 인터페이스에 드러나는가
- 변경의 호출자, 소비자, 다른 서비스·배포 단위와 운영 확인 경로가 빠지지 않았는가

계약이나 소유권이 불명확해 실패 수렴을 보장할 수 없으면 테스트 부족보다 인터페이스·책임 경계 결함을 먼저 보고하라. 외부 상태 변경을 DB 트랜잭션 안에서 실행하면서 결과 조회 계약이나 결과 불명을 복구할 영속 기록이 없다면 트랜잭션·실패 수렴 결함이다. 대역의 내부 맵만 중복을 막고 실제 포트에는 업무 멱등 키나 결과 조회 계약이 없다면 대역 테스트 통과와 무관하게 인터페이스 결함이다. 비동기 소비자가 읽은 오래된 전체 상태를 저장해 동시 변경을 덮을 수 있다면 상태 소유권·쓰기 경계 결함으로 보고, 실제 저장소 조건의 경합 테스트 누락을 별도 검증 근거로 연결하라.

이후 전체 브랜치를 다음 관점에서 검토하라. 작업과 관련 없는 관점은 억지로 채우지 말라.

### 의도와 범위

- 백로그의 배경과 목표를 충족하는가
- 명시적 비범위나 요청하지 않은 변경을 침범하지 않았는가

### 정확성과 근본 원인

- 핵심 로직과 상태 전이가 모든 관련 경로에서 올바른가
- 수정 지점이 근본 원인과 일치하는가
- 예외, 경계값, 부분 실패와 복구가 빠지지 않았는가

### 영향 전파와 회귀

- 호출자, 소비자, 데이터와 외부 인터페이스에 미치는 영향이 안전한가
- 호환성, 마이그레이션 또는 롤백 문제가 없는가
- 인접 기능에서 예상하지 못한 동작 변화가 생기지 않는가

### 재발 방지와 검증

- 테스트가 구현 세부사항이 아니라 원인과 불변 조건을 검증하는가
- 위험 작업에서 정상 흐름과 단순 예외만 검증하고 응답 유실, 부분 성공, 프로세스 재시작, 중복·역순 사건 또는 실제 저장소 경합처럼 관련 있는 실패 모드를 빠뜨리지 않았는가
- 같은 결함이 다른 경로에서 재발할 가능성이 남아 있지 않은가
- 관측 가능성이나 실패 진단에 필요한 정보가 충분한가

### 설계와 유지보수

- 책임, 추상화와 모듈 경계가 작업 의도에 맞는가
- 불필요한 결합, 중복 또는 변경 확산을 만들지 않았는가
- 미래 변경에서 같은 문제를 반복하기 쉬운 구조가 아닌가

### 상황별 위험

관련 있을 때만 보안, 개인정보, 성능, 동시성, 트랜잭션, 자원 정리와 운영 위험을 검토하라. 원격 상태 변경, 메시지·웹훅·워커, 여러 트랜잭션이나 서비스에 걸친 결과, 병렬 명령, 마이그레이션·순차 배포 또는 신뢰 경계 입력이 보이면 해당 위험을 심화 검토하라.

## 5. 증거와 검증

- 발견 사항은 구체적인 파일과 가능한 한 좁은 줄 위치를 근거로 제시하라.
- 사실, 코드에서 도출한 추론과 확인하지 못한 가정을 구분하라.
- 재현 또는 검증에 도움이 되는 로컬 테스트·정적 검사 명령을 실행할 수 있다.
- 리뷰를 위해 소스나 테스트를 수정하지 말라.
- 근거 없는 가능성이나 일반적인 스타일 선호를 결함처럼 보고하지 말라.
- 발견 사항이 없으면 없다고 명확히 말하고 남은 테스트 공백이나 확인하지 못한 위험만 적어라.

심각도는 다음 기준을 사용하라.

- **치명:** 데이터 손실, 보안 침해, 광범위한 장애처럼 즉시 차단해야 하는 문제
- **높음:** 핵심 기능 오류나 높은 회귀 가능성으로 병합 전에 수정해야 하는 문제
- **중간:** 특정 조건에서 오동작하거나 유지보수 위험을 실질적으로 높이는 문제
- **낮음:** 영향은 제한적이지만 수정 가치가 분명한 문제

## 6. 전체 결과 보고

항목별 결정을 묻기 전에 모든 발견 사항을 심각도 순으로 먼저 보고하라. 장황한 과정 설명보다 리뷰 결론과 증거를 우선하라. 각 발견 사항에는 현재 백로그의 완료를 막는지와 그 근거를 반드시 표시하라. 심각도만으로 완료 차단 여부를 기계적으로 정하지 말고, 해당 문제가 백로그 목표와 완료 기준을 충족하지 못하게 하는지를 근거로 판정하라.

```text
리뷰 대상
- 백로그: BL-NNNN 제목
- 브랜치: feature/bl-NNNN-title
- 기준 브랜치: main
- 커밋: N개

발견 사항
[높음] 짧은 제목
- 위치: path/to/File.ext:line
- 관찰: 코드에서 확인한 사실
- 인과 관계: 원인 → 전파 → 결과
- 영향: 사용자 또는 시스템에 미치는 문제
- 완료 차단: 예 / 아니오 — 판정 근거
- 권장 조치: 수정 방향

커밋별 평가
- abc1234 feat(bl-NNNN): 한국어 요약 — 평가

게이트 판단
- 구현 준수: 통과 / 실패 — 근거
- 인터뷰 완전성: 통과 / 실패 — 근거

검증과 남은 위험
- 실행한 검사와 결과
- 확인하지 못한 영역

최종 판단
- 승인 가능 / 수정 후 재검토 / 사용자 결정 필요
```

최종 판단은 항목별 완료 차단 판정에서 도출하라. 처분 전 시점에 완료 차단 발견 사항이 하나라도 있으면 `수정 후 재검토`, 없으면 `승인 가능`으로 판정한다. 코드만으로 완료 차단 여부를 정할 수 없어 사용자의 제품·정책 판단이 필요한 경우에만 `사용자 결정 필요`로 판정하라.

파일이나 GitHub에 리뷰 결과를 작성하지 말고 채팅 응답으로만 제공하라.

발견 사항이 있으면 같은 응답의 마지막에서 가장 심각도가 높은 첫 항목의 인터뷰를 바로 시작하라. 사용자에게 인터뷰 시작을 다시 요청하게 만들지 말라. 발견 사항이 없으면 항목별 인터뷰를 만들지 말고 완료 게이트에서 백로그 이동과 커밋 승인을 요청하라.

## 7. 발견 사항별 인터뷰

전체 결과를 이미 보고한 뒤 발견 사항을 심각도 순으로 하나씩 다뤄라. 관련된 발견 사항이어도 사용자의 처분 결정은 항목별로 받는다.

각 항목에서는 다음을 간결하게 다시 제시하라.

- 문제의 배경과 코드 근거
- 원인에서 사용자·시스템 영향으로 이어지는 인과 관계
- 현재 백로그 완료를 막는지 여부와 그 이유
- 권장 조치와 적용 시 핵심 영향

그다음 사용자에게 다음 네 가지 중 하나를 선택하게 하라.

- **반영:** 현재 리뷰 대상 브랜치와 같은 `BL-NNNN` 범위에서 수정한다.
- **보류:** 이번에는 수정하지 않고 보류 이유와 미해결 위험을 최종 요약에 남긴다.
- **후속 백로그:** 현재 범위 밖의 독립 작업으로 분리한다. 최종 계획 승인 후 `$capture-backlog` 절차로 기록한다.
- **기각:** 지적을 받아들이지 않는다. 사용자의 판단 근거와 수용한 위험을 최종 요약에 남긴다.

사용자의 결정을 기록만 하고 다음 항목으로 넘어가라. 인터뷰 중에는 선택한 수정이나 백로그 생성을 실행하지 말라. 사용자는 최종 승인 전까지 앞선 결정을 바꿀 수 있다.

사용자가 인터뷰를 중단하면 지금까지 확정한 결정과 남은 항목을 구분해 요약하고 멈춰라. 미결정 항목을 임의로 분류하거나 적용 단계로 넘어가지 말라.

## 8. 최종 반영 계획 승인

모든 항목의 처분이 정해지면 다음을 한 번에 요약하라.

- 반영할 발견 사항과 수정 범위
- 보류할 발견 사항, 이유와 남은 위험
- 후속 백로그로 기록할 독립 항목
- 기각한 발견 사항과 판단 근거
- 수행할 표적 검증과 관련 저장소 검증 명령
- 예상 커밋 경계와 현재 백로그의 완료 가능 여부

이 계획대로 진행해도 되는지 사용자에게 명시적으로 물어라. 승인 전에는 소스, 테스트, 백로그 파일을 수정하거나 커밋하지 말라. 사용자가 계획 일부를 바꾸면 요약을 갱신하고 다시 승인받아라.

## 9. 승인된 결정 일괄 반영

최종 승인 후 승인된 결정만 전체 맥락에 맞춰 일괄 반영하라.

- 현재 브랜치, 기준 브랜치, 작업 트리와 리뷰 대상 커밋이 인터뷰 당시와 같은지 다시 확인하라. 달라졌으면 영향을 설명하고 사용자에게 확인받아라.
- `반영` 항목은 현재 백로그 목표에 필요한 수정으로 다루고 같은 `BL-NNNN`을 포함한 리뷰 가능한 커밋으로 정리하라.
- `후속 백로그` 항목은 사용자가 최종 승인한 내용만 `$capture-backlog`로 기록하라. 현재 소스 수정과 별도 작업을 섞지 말라.
- 보류·기각한 항목은 수정하지 말라.
- 구현 중 새로운 중요한 결정이 나타나면 멈추고 선택지와 추천안을 사용자에게 물어라.
- 수정 후에는 승인된 발견 사항이 해결됐는지 표적 검증하고 관련 테스트와 저장소 검증 명령을 실행하라.
- 전체 RCA 리뷰를 자동으로 다시 실행하지 말라. 사용자가 `$rca-code-review`를 다시 요청했을 때만 전체 재리뷰를 수행하라.
- 수정 사항은 검증과 완료 게이트 처리가 끝나기 전에 커밋하지 말라. 적용, 표적 검증, 완료 판정과 승인 확인, 백로그 이동, 스테이징과 커밋 순서로 진행하라.

커밋과 스테이징은 대상 프로젝트의 로컬 규칙을 우선한다. 별도 규칙이 없으면 검증과 완료 게이트 처리 후 변경한 파일만 명시적으로 스테이징하고 `<type>(bl-NNNN): <한국어 요약>` 형식을 사용한다. 기존 커밋을 명시적 요청 없이 amend, rebase, squash 또는 삭제하지 말고 push나 PR 생성으로 확대하지 말라.

## 10. 완료 게이트와 백로그 이동

`docs/backlog/done` 이동은 코드 리뷰가 구현 완료를 확인하는 단계다. 대상 프로젝트에 다른 백로그 규약이 있으면 그 규약을 우선한다.

- 발견 사항이 없고 관련 검증이 통과하면 완료할 수 있다.
- 승인된 `반영` 항목의 수정과 표적 검증이 모두 통과하고 완료를 막는 미해결 항목이 없으면 완료할 수 있다.
- 리뷰 최종 판단이 `수정 후 재검토`인 항목을 보류해 미해결 상태로 남겼거나 검증이 실패하면 열린 상태를 유지한다.
- 현재 범위 밖의 `후속 백로그`는 원래 백로그 완료를 막지 않는다.
- 사용자가 근거를 확인하고 지적을 `기각`하면 그 항목은 완료를 막는 미해결 항목으로 보지 않되, 수용한 위험을 완료 보고에 남긴다.

완료할 수 있다고 판정하면 백로그 이동, 포함할 커밋과 검증 결과를 요약하고 사용자에게 명시적으로 완료 승인을 요청하라. 발견 사항이 있는 경우에는 8단계의 최종 반영 계획 승인에 이 내용을 포함하고, 발견 사항이 없는 경우에는 별도로 승인받는다.

완료 승인 후 열린 백로그 파일을 내용 수정 없이 `git mv docs/backlog/bl-NNNN-*.md docs/backlog/done/`으로 옮긴다. 그다음 검증을 통과한 소스 수정과 완료 이동을 함께 스테이징하고 마지막 관련 커밋으로 남긴다. 소스 수정이 없으면 완료 이동만 같은 `BL-NNNN`의 명시적인 문서 커밋으로 남긴다. 검증 실패, 사용자 중단 또는 완료 미승인 시에는 옮기거나 커밋하지 않는다.

과거 절차로 이미 `done`에 있는 항목을 리뷰할 때 완료 차단 문제가 발견되면 인터뷰와 최종 계획 승인 후 적용 전에 열린 위치로 되돌린다. 차단 문제가 없으면 기존 위치를 유지한다.

## 11. 완료 보고

적용과 완료 판단이 끝나면 다음을 채팅에 보고하라.

- 항목별 최종 결정과 실제 반영 결과
- 생성한 커밋의 짧은 해시, 메시지와 검증 결과
- 보류·기각한 위험과 생성한 후속 백로그 ID
- 백로그가 열린 상태인지 `done`으로 이동했는지와 그 이유
- 전체 재리뷰는 자동 수행하지 않았으며 원할 경우 명시적으로 요청할 수 있다는 안내

리뷰와 반영 과정 전체에서 GitHub 리뷰나 별도 결과 문서를 만들지 말라.
