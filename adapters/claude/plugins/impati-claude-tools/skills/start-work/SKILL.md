# Start Work Interview

기능 동작에 영향을 주는 코드 작업을 시작하기 전에 사용자의 의도를 충분히 이해하고 주요 결정을 합의하라. 인터뷰와 최종 승인이 끝나기 전에는 구현하지 말라.

## 기본 원칙

- 사용자의 원래 요청보다 넓은 작업을 제안하거나 실행하지 말라.
- 질문으로 사용자의 생각을 대신 결정하지 말고, 선택 가능한 방향과 영향을 드러내라.
- 결과에 영향을 줄 수 있는 결정은 사용자에게 묻고 진행하라.
- 결정의 중요도가 불분명하면 질문하는 쪽을 선택하라.
- 변수명처럼 쉽게 되돌릴 수 있는 세부사항까지 기계적으로 질문하지 말라. 대신 에이전트에게 위임할 세부사항의 기본 방침을 최종 브리프에 명시하라.
- 이미 답변된 내용을 다시 묻지 말고, 대화와 저장소에서 확인 가능한 사실을 먼저 활용하라.
- 사용자가 충분하다고 판단할 때까지 인터뷰 깊이를 조정하라. 처음부터 완벽한 경계를 가정하지 말고 실제 피드백으로 개선하라.

## 1. 안전하게 컨텍스트 수집

인터뷰 전에 필요한 범위에서 저장소를 읽기 전용으로 조사하라.

- 대상 저장소 루트의 `AGENTS.md`를 레포 고유 기술 지침의 표준 진입점으로 읽고, 변경 경로에 적용되는 더 구체적인 `AGENTS.md`와 관련 문서를 함께 읽어라.
- 루트 `AGENTS.md`가 없으면 코드, ADR, 빌드 파일과 기존 관례를 조사하되 레포 고유 기준을 만들어내지 말라. `CLAUDE.md`처럼 특정 에이전트 전용 파일을 공통 정본으로 가정하지 말라.
- 저장소 구조, 변경 상태, 관련 코드와 테스트를 확인하라.
- 기존 구현과 제약을 확인하되 파일 수정, 의존성 설치, 외부 상태 변경은 하지 말라.
- 조사로 알 수 있는 사실을 사용자에게 질문하지 말라.

## 2. 백로그 연결 확인

모든 기능 코드 작업을 하나의 `BL-NNNN` 백로그 항목과 연결하라.

- 사용자 요청, 현재 브랜치와 대화에서 백로그 ID를 확인하라.
- ID가 있으면 `docs/backlog/bl-NNNN-*.md` 항목을 읽고 배경과 목표를 인터뷰 컨텍스트로 사용하라. 열린 항목에 없으면 `docs/backlog/done/bl-NNNN-*.md`도 확인하라.
- 항목이 이미 `docs/backlog/done`에 있으면 완료된 작업이므로, 이어서 작업할지 새 백로그 항목을 만들지 사용자에게 확인하라. 같은 항목을 이어서 작업하기로 확정하면 최종 브리프 승인 후 구현 전에 열린 위치로 되돌려라.
- ID가 없으면 구현이나 브랜치 생성을 시작하지 말고 `capture-backlog`로 항목을 먼저 생성하라.
- 백로그 항목 생성 커밋이 안전한 기준 브랜치에 반영된 뒤 인터뷰를 계속하라.
- ID가 존재하지 않거나 여러 항목과 모호하게 일치하면 사용자에게 확인하라.
- 하나의 기능 코드 작업을 여러 백로그 ID에 임의로 연결하지 말라. 범위가 독립적이면 작업과 브랜치를 나눌지 사용자에게 물어라.

## 3. 의도 재진술

먼저 다음 내용을 짧게 재진술하고 사용자가 바로잡을 기회를 제공하라.

- 해결하려는 문제와 기대하는 결과
- 요청에 포함된 범위와 포함되지 않은 것으로 보이는 범위
- 현재까지 확인한 제약과 가정
- 완료되었다고 판단할 기준

의도가 틀렸거나 빠진 부분이 있으면 수정된 내용을 다시 요약하라.

## 4. 결정 지도 작성

아래 영역 중 작업 결과에 관련된 항목을 식별하라. 체크리스트를 기계적으로 전부 질문하지 말고, 관련성과 영향이 있는 결정을 빠짐없이 찾아라.

- 사용자 가치와 성공 기준
- 기능 범위와 명시적 비범위
- 사용자 흐름, API 또는 인터페이스 동작
- 데이터 모델, 상태, 마이그레이션과 호환성
- 아키텍처, 모듈 경계와 의존성
- 오류 처리, 예외 상황과 복구 방식
- 보안, 개인정보, 권한과 파괴 가능성
- 성능, 동시성, 운영과 관측 가능성
- 테스트 수준, 검증 명령과 수용 기준
- 배포, 점진 적용, 롤백과 문서화
- 커밋 컨벤션, 리뷰 단위와 커밋 경계
- 백로그 ID, feature 브랜치 이름과 기준 브랜치

확정할 규칙 중 코드에서 유도되지 않고 사람이 정해야 하는 비즈니스 규칙이 있으면 정책 결정 문서가 필요한지 판정하라. 필요해 보이면 근거와 함께 `decide-policy`를 제안하고, 사용자가 승인할 때만 진입하라. 자동으로 정책 문서를 만들지 말라.

저장소 조사에서 발견한 제약 때문에 선택지가 제한된다면 그 근거를 설명하라.

## 5. 상세 인터뷰 진행

한 번에 하나의 결정 주제에 집중하라. 관련 질문은 작은 묶음으로 물을 수 있지만 서로 다른 결정을 한꺼번에 쏟아내지 말라.

각 결정 질문에는 가능한 경우 다음을 포함하라.

1. 이 결정이 필요한 이유
2. 2~3개의 실제로 가능한 선택지
3. 각 선택지가 결과에 미치는 핵심 장단점
4. 추천안과 현재 컨텍스트에서 추천하는 이유
5. 사용자가 직접 선택하거나 에이전트에게 위임할 수 있다는 안내

선택지가 하나뿐이면 억지 대안을 만들지 말고 제약과 이유를 설명한 뒤 확인받아라. 사용자의 답변이 새로운 모호함이나 결정을 만들면 후속 질문을 이어가라.

## 6. 시스템 관점 검토

기능 질문을 마친 뒤 최종 구현 승인을 요청하기 전에 변경이 시스템 전체에서 성립하는지 한 번 검토하라. 아래 관점을 고정 질문처럼 사용자에게 읽어 주지 말고, 코드와 레포 지침에서 먼저 조사한 뒤 결과를 바꾸는 결정만 질문하라.

- 변경이 통과하는 시스템, 모듈, 프로세스와 데이터 저장소 및 각 경계
- 상태와 사실의 정본, 쓰기 권한, 트랜잭션과 원자성의 경계
- 동기 호출, 비동기 사건과 외부 부수효과가 성공, 실패, 결과 불명과 중단 후 재개에서 수렴하는 방식
- 중복, 순서 역전, 동시 실행, 재시도, 부분 성공과 데이터 불일치의 처리 주체
- 대역, 어댑터나 하위 시스템으로 캡슐화하는 보장과 애플리케이션이 직접 책임지는 보장
- 변경의 호출자와 소비자, 다른 서비스·배포 단위·운영 흐름 및 관측·운영 확인 경로
- 기존 데이터 변환이나 순차 배포 호환성이 실제 범위에 포함되는지 여부

각 관련 관점에는 코드, 적용되는 레포 지침 또는 사용자 결정 중 적어도 하나의 근거가 있어야 한다. 관련 없는 관점은 억지로 확장하지 말고, 해당 없다고 판단한 근거만 짧게 남겨라. 미결정 사항이 구현 결과를 바꿀 수 있으면 최종 승인으로 넘어가지 말라.

### 위험 신호에 따른 심화

다음 신호가 코드나 요청에서 확인될 때만 해당 관점을 확장하라.

- 원격 시스템이나 외부 업체의 상태를 바꾸는 호출
- 메시지, 웹훅, 스케줄러, 워커 또는 Outbox/Inbox
- 둘 이상의 DB 트랜잭션이나 서비스가 하나의 업무 결과를 나눠 가지는 흐름
- 낙관적·비관적 잠금 또는 같은 자원에 대한 병렬 명령
- 마이그레이션, 기존 데이터 변환 또는 순차 배포 호환성
- 인증, 서명, 재전송 공격처럼 신뢰 경계를 넘는 입력

외부 부수효과가 있으면 최소한 업무 멱등 키의 소유자와 전달 계약, 같은 키 재호출의 의미, 외부 결과 조회 가능성, 응답 유실 뒤 복구, 로컬 커밋과 외부 결과의 순서를 확인하라. 외부 변경을 DB 트랜잭션 안에서 실행하면서 결과 불명을 판별할 계약이나 영속 복구 경로가 없다면 미결정 결함으로 보고 최종 계획 승인을 요청하지 말라. 대역 구현의 내부 자료구조가 우연히 중복을 막는 것은 포트 계약의 멱등성 보장이 아니다.

비동기 소비나 동시 쓰기가 있으면 사건의 순서와 중복뿐 아니라 소비자가 읽은 오래된 전체 상태를 저장해 다른 변경을 덮어쓸 가능성, 실제 저장소의 잠금·버전 조건과 재시도 수렴을 확인하라.

### 불변식과 테스트 의무

최종 구현 계획의 핵심 불변식과 실패 수렴마다 이를 깨뜨려 검증하는 자동 테스트 의무를 대응시켜라. 라인·브랜치 커버리지 수치는 완료 기준을 대신하지 않는다.

- 원격 변경이 관련되면 응답 유실 뒤 조회·재시도 복구, 같은 멱등 키 재사용, 로컬 커밋 실패와 프로세스 재시작 중 실제로 가능한 항목을 테스트 의무로 검토하라.
- 비동기 소비나 동시 쓰기가 관련되면 중복·역순 사건과 실제 저장소의 잠금·버전 조건을 통과하는 경합 중 가능한 항목을 검토하라.
- 정상 흐름, 단순 재호출 또는 예외 한 번만 검증하고 관련 실패 모드를 빠뜨린 위험 작업은 구현 완료 기준으로 승인하지 말라.

## 7. 미결정 사항 점검

인터뷰가 끝났다고 판단하기 전에 다음을 점검하라.

- 목표, 범위, 비범위와 완료 기준이 서로 모순되지 않는가
- 중요한 선택이 암묵적 가정으로 남아 있지 않은가
- 사용자가 에이전트에게 위임한 결정과 그 기본 방침이 명확한가
- 관련 시스템 관점마다 코드·레포 지침·사용자 결정 중 하나의 근거가 있고, 위험 신호에 대응하는 불변식·실패 수렴·테스트 의무가 연결됐는가
- 위험하거나 되돌리기 어려운 변경이 명시적으로 승인되었는가
- 테스트와 검증 방법이 합의되었는가

미결정 사항이 있으면 구현으로 넘어가지 말고 질문하라.

## 8. 최종 작업 브리프 승인

인터뷰 결과를 다음 구조로 간결하게 정리하라.

- **의도:** 해결하려는 문제와 사용자 가치
- **백로그:** `BL-NNNN` ID, 제목과 문서 경로
- **범위:** 이번 작업에 포함할 내용
- **비범위:** 의도적으로 하지 않을 내용
- **결정:** 선택한 방향과 이유
- **위임된 결정:** 에이전트가 판단해도 되는 세부사항과 기본 방침
- **완료 기준:** 검증 가능한 결과
- **시스템 근거:** 아래 근거 표. 각 항목은 관련 코드·레포 지침·사용자 결정과 테스트 의무까지 짧게 연결
- **커밋 계획:** 예상되는 논리적 리뷰 단위와 적용할 커밋 컨벤션
- **브랜치 계획:** 기준 브랜치와 생성할 feature 브랜치
- **위험과 제약:** 남아 있는 트레이드오프 또는 주의점

```text
| 항목 | 근거와 결정 |
| --- | --- |
| 영향 경계 | 바뀌는 시스템·소유 상태·호출자와 소비자 |
| 핵심 불변식 | 반드시 함께 성립하거나 절대 중복되면 안 되는 사실 |
| 실패 수렴 | 실패·결과 불명·중단·경합 뒤 근거 기록과 목표 상태 |
| 테스트 의무 | 각 불변식과 실패 수렴을 깨뜨려 검증할 자동 테스트 |
| 레포 근거 | 적용한 AGENTS.md, ADR, 기존 패턴과 검증 명령 |
```

표를 장문의 체크리스트나 조사 일지로 만들지 말라. 단순 로컬 변경이라 관련 위험이 없다면 영향 경계와 해당 없음의 근거를 짧게 기록하는 것으로 충분하다.

사용자에게 이 브리프로 작업을 시작해도 되는지 명시적으로 물어라. 승인 전에는 ADR이나 구현 파일을 작성하지 말라.

## 9. feature 브랜치 생성

최종 작업 브리프 승인 후 구현 전에 백로그 ID가 포함된 feature 브랜치를 준비하라.

- 대상 프로젝트의 로컬 브랜치 규칙을 우선하라.
- 별도 규칙이 없으면 `feature/bl-NNNN-kebab-case-title` 형식을 사용하라.
- 브랜치 제목은 백로그 파일 제목을 기반으로 짧게 작성하라.
- 브랜치를 만들기 전에 현재 브랜치, 기준 브랜치와 작업 트리 상태를 확인하라.
- 다른 작업의 변경이 있거나 안전한 기준 브랜치를 판단할 수 없으면 사용자에게 물어라.
- 같은 이름의 브랜치가 있으면 덮어쓰지 말고 기존 브랜치를 이어갈지 새 이름을 사용할지 확인하라.
- 이미 올바른 백로그 feature 브랜치에 있다면 새로 만들지 말고 계속 사용하라.
- 자동으로 push하지 말라.

## 10. ADR 기록

사용자가 최종 브리프를 승인하면 대상 프로젝트의 로컬 규칙에서 ADR을 요구하거나 허용하는지 확인하라. ADR을 사용하는 프로젝트에서는 구현 전에 `references/adr-convention.md`를 읽고 `docs/adr`에 ADR을 작성하라.

- 인터뷰에서 실제로 논의하고 승인한 내용만 기록하라.
- ADR을 진행 일지나 상세 구현 문서로 만들지 말라.
- 새 ADR 파일 자체는 승인된 작업의 첫 변경으로 간주하라.
- 저장소에 다른 ADR 규약이 있으면 더 가까운 저장소 규약을 우선하라.
- 대상 프로젝트가 ADR을 사용하지 않으면 최종 작업 브리프를 대화에 유지하고 ADR 작성 없이 구현으로 넘어가라.

## 11. 승인된 범위로 실행

필요한 ADR을 작성했거나 로컬 규칙에 따라 생략한 뒤 승인된 범위 안에서만 구현하라.

- 구현 중 새로운 중요한 결정이 나타나면 작업을 멈추고 선택지와 추천안을 사용자에게 물어라.
- 새 결정이 승인되면 ADR을 사용하는 프로젝트에서는 같은 ADR의 `추가 결정`에 반영하라. ADR을 사용하지 않으면 대화의 최종 작업 브리프를 갱신한 뒤 계속하라.
- 단순한 가역적 세부 구현은 승인된 위임 방침에 따라 처리하라.
- 합의한 구현 완료 기준과 근거 표의 테스트 의무로 검증하라. 위험 작업의 관련 불변식이나 실패 수렴에 대응하는 자동 테스트가 빠졌으면 정상 흐름 테스트가 통과해도 완료로 보지 말라.
- 검증을 통과해도 백로그 항목은 열린 위치에 유지하라. 구현 완료는 코드 리뷰 완료가 아니며, 사용자가 명시적으로 요청한 `rca-code-review`가 완료 판단과 `docs/backlog/done` 이동을 담당한다.
- 검증이 실패했거나 사용자가 작업을 중단해도 열린 상태를 유지하라.
- 대상 저장소에 다른 백로그 관례가 있으면 그 관례를 우선하고, `docs/backlog` 또는 `docs/backlog/done`을 임의로 만들지 말라.
- 이 하네스 저장소 자체의 작업이면 `CHANGELOG.md`도 갱신하라. 대상 프로젝트가 변경 기록을 관리하지 않으면 `CHANGELOG.md`를 새로 만들거나 갱신을 요구하지 말라.

## 12. 리뷰 단위로 커밋하고 보고

검증이 끝나면 현재 작업의 변경을 사용자가 커밋별로 리뷰할 수 있도록 정리하라.

### 커밋 경계 결정

- 하나의 커밋에는 하나의 설명 가능한 작업 의도를 담아라.
- 각 커밋이 가능한 한 독립적으로 이해되고 검증되며 되돌려질 수 있게 하라.
- 구현과 그 구현을 증명하는 테스트는 특별한 이유가 없으면 같은 커밋에 포함하라.
- 파일 종류만을 기준으로 기계적으로 나누지 말라. 분리하면 중간 커밋이 깨지거나 의미가 불완전해지는 변경은 함께 커밋하라.
- 서로 독립적인 기능, 수정, 리팩터링 또는 문서 변경은 별도 리뷰가 유용하면 나누어라.
- 커밋 수를 늘리는 것 자체를 목표로 삼지 말라. 작은 단일 의도의 작업은 하나의 커밋이면 충분하다.

### 안전하게 스테이징

- 커밋 전에 `git status`와 diff를 확인하라.
- 현재 작업에서 생성하거나 수정한 변경만 스테이징하라.
- 사용자가 만든 기존 변경이나 다른 작업의 변경을 임의로 포함하거나 되돌리지 말라.
- 같은 파일에 현재 작업과 기존 변경이 섞여 안전하게 분리할 수 없으면 사용자에게 물어라.
- 광범위한 자동 스테이징보다 명시적인 파일이나 검토한 hunk를 선택하라.
- 비밀, 인증 정보, 생성물 또는 로컬 전용 파일이 포함되지 않았는지 확인하라.

### 커밋 생성

- 대상 프로젝트의 로컬 커밋 규칙과 메시지 컨벤션을 우선하라.
- 모든 기능 코드 커밋에 현재 `BL-NNNN` 추적 ID를 포함하라.
- 별도 컨벤션이 없으면 `<type>(bl-NNNN): <한국어 요약>` 형식을 사용하라.
- `type`은 작업 의도에 맞춰 `feat`, `fix`, `refactor`, `test`, `docs`, `chore` 등에서 선택하라.
- 요약은 간결한 한국어로 작성하라.
- 각 커밋을 만들기 전에 staged diff가 해당 의도와 일치하는지 확인하라.
- 가능한 범위에서 각 커밋 단위의 관련 검증을 수행하라.
- 사용자가 커밋하지 말라고 했거나 로컬 규칙이 자동 커밋을 금지하면 커밋하지 말고 변경 상태를 보고하라.
- 명시적 요청 없이 기존 커밋을 amend, rebase, squash 또는 삭제하지 말라.
- push, 브랜치 생성과 PR 생성은 별도 요청이 있을 때만 수행하라.

### 완료 보고

생성한 순서대로 각 커밋을 보고하라.

- 짧은 커밋 해시와 메시지
- 해당 커밋의 작업 의도와 핵심 변경
- 수행한 검증과 결과
- 남아 있는 미커밋 변경과 그 이유
- 백로그 ID와 문서 경로
- 작업 브랜치 이름
- 구현 검증은 끝났지만 코드 리뷰 전이므로 백로그가 열린 상태라는 점

커밋이 하나여도 같은 형식으로 보고하라.

## 13. 다음 단계 안내

작업과 커밋 보고가 끝나면 백로그 완료를 위해 `$rca-code-review`로 브랜치를 커밋별·누적 관점에서 리뷰할 수 있음을 한 문장으로 안내하라.

- 코드 리뷰를 자동 실행하지 말라.
- 사용자가 `$rca-code-review` 또는 코드 리뷰를 명시적으로 요청했을 때만 리뷰를 시작하라.
- 사용자가 리뷰를 요청하지 않으면 백로그는 열린 상태로 남는다.
- GitHub 리뷰, push 또는 PR 생성으로 확대하지 말라.

## 빠른 경로

사용자의 요청과 현재 대화가 이미 위 절차에 준하는 목표, 범위, 주요 결정, 완료 기준과 승인을 포함한다면 질문을 반복하지 말라. 확인된 내용을 최종 브리프로 통합해 승인 여부만 확인하거나, 명시적 승인이 이미 있다면 ADR 작성부터 진행하라.

사용자가 인터뷰를 생략하라고 명시하면 생략 범위와 그로 인해 에이전트에게 위임되는 결정을 짧게 확인하고 사용자의 지시를 우선하라.
