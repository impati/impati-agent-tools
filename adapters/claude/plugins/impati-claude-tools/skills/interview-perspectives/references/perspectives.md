# 관점별 충족 기준

전체 관점의 관련성을 확인한 뒤 결과를 바꾸는 영역만 심화한다. 아래 예시는 고정 질문이나 모든 프로젝트의 필수 구현 요구가 아니다. 기존 코드·계약·사용자 합의로 충분하면 추가 질문 없이 근거를 연결한다.

## 관점 목록

| 관점 | 인터뷰에서 확인돼야 할 내용 |
| --- | --- |
| 목적·범위·정책 | 누구의 어떤 문제를 해결하는지, 성공·비범위, 허용·거절할 업무 동작과 결정 권한. 법적·조직 제약은 적용 근거가 있을 때 확인하며 임의로 만들지 않는다. |
| 사용자 경험·접근성 | 주요 사용자의 흐름, 오류·빈 결과·대기·취소와 완료 표시. 관련 사용 환경의 접근성·언어·시간대 요구가 결과에 미치는 영향. |
| 시스템 아키텍처·책임 | 구성 요소·호출자·소비자의 경계, 상태 정본과 쓰기 책임, 인터페이스 보장, 외부 의존성·장애 전파와 기존 구조에 맞춘 선택 이유. |
| 데이터 생명주기·파기 | 생성·수집부터 이용·변경·복제·보관·만료·삭제·복원까지의 흐름, 데이터별 소유자·보관 근거·파기 책임과 검증 가능한 완료 의미. |
| 정합성·동시성·장애 복구 | 트랜잭션·외부 부수효과 경계, 중복·역순·경합·부분 성공·결과 불명·중단 후 재개에서 유지할 불변식과 수렴 책임. |
| 성능·용량·비용 | 실제 사용량·데이터 규모·동시성·증가 예상에 맞춘 지연·처리량·자원·비용 제약과 측정 방법. 부하 초과 시 허용 동작과 비용의 책임. |
| 보안·개인정보·악용 방지 | 보호할 자산·신뢰 경계·입력·권한, 관련 공격·오용 상황과 차단 기대 동작. 수집 최소화, 노출 범위와 민감정보 취급 근거. |
| 운영·관측·지원 | 실패를 감지·추적할 신호, 완료·실패 상태를 확인할 경로, 대응 주체와 안전한 재처리·수동 복구 방법. |
| 배포·호환성·롤백 | API·이벤트·기존 데이터·클라이언트의 호환성, 혼합 버전 운영, 마이그레이션·전환·롤백 또는 전진 복구 조건. |
| 유지보수·변경 가능성 | 관련 모듈의 책임·의존 방향, 변경 영향과 테스트 대역의 한계, 의존성·설정의 소유자. 예상되는 구체 변화가 있을 때만 확장 지점을 검토한다. |
| 검증·완료 | 각 중요한 요구·불변식을 어떤 정상·경계·실패 사례로 검증할지, 필요한 환경·자료와 미검증 영역. 명확한 요구와 구현 검증 통과를 구분한다. |

## 시스템 아키텍처

경계나 외부 의존성이 바뀔 때 요청이 거치는 구성 요소, 상태 소유자와 계약을 추적한다. 호출자가 기대하는 보장을 실제 제공하는 주체와 연결하라. 외부 서비스나 라이브러리가 보장하는 것과 애플리케이션의 책임을 구분한다.

동기·비동기 처리, 트랜잭션 분리, 캐시·복제본·이벤트의 정본, 장애 전파와 자원 격리 중 관련 결정을 확인한다. 레포의 기존 패턴을 선택 근거로 조사하되 새 요구에 적합한지 검토하라. 관점을 충족하려고 새 서비스·계층·추상화를 만들거나 기술을 먼저 고르게 하지 말라.

기능 코드 인터뷰의 불변식·멱등성·결과 불명·경합에 관한 필수 기준은 기본 `interview`가 연결한 시스템 검토를 함께 적용한다. 여기의 목록으로 그 기준을 축약하지 않는다.

## 데이터 생명주기와 파기

데이터를 저장·복제하거나 삭제 의미가 바뀌면 데이터 종류별로 다음 흐름 중 관련 부분을 연결하라.

`생성·수집 → 사용·변경 → 복제·파생 → 보관·만료 → 삭제·파기 → 백업 복원 시 처리`

- 원본뿐 아니라 캐시, 검색 인덱스, 객체 저장소, 분석 데이터, 이벤트·로그, 외부 수탁 시스템과 백업에 남는 사본을 조사하라. 모두 존재한다고 가정하지 말고 실제 경로를 확인한다.
- 삭제 요청, 접근 차단, 논리 삭제, 물리 파기와 사용자에게 보여 줄 완료 시점을 구분하라. 누가 어떤 계기로 파기를 시작하고, 언제까지 어느 사본이 없어져야 하는지 합의한다.
- 보관 기간·예외·감사 증적에 필요한 최소 데이터와 책임 주체를 확인하라. 법정 기간이나 규제 적용을 추측하지 말고 적용 근거를 조사하거나 확인이 필요하다고 남긴다.
- 일부 사본의 삭제 실패, 재시도·중복 요청, 동시 쓰기와 진행 중 작업, 백업 복원으로 삭제 데이터가 다시 나타나는 상황의 기대 동작을 확인하라.
- 예를 들어 "탈퇴하면 DB에서 삭제"만으로 파기를 확인 처리하지 말라. 관련 복제본·백업의 처리 계약이 없으면 결정 또는 근거가 부족한 것이다. 실제 데이터를 삭제하거나 백업을 복원하는 작업은 인터뷰 범위가 아니다.

## 성능·용량·비용

성능에 영향이 있으면 대표 사용 흐름·피크 부하·데이터 규모를 먼저 확인하라. 요청·쿼리 수 증가, 팬아웃, 큰 목록·파일, 배치, 잠금 경합, 큐 적체와 외부 제한 중 실제 위험을 조사한다.

"빠르게"라는 요구는 관련 흐름의 지연 분포·처리량·자원 상한 등 관찰 가능한 기준과 측정 환경으로 구체화하라. 기준값은 사용자 요구·기존 계약·측정 근거로 정하며 임의의 숫자를 넣지 않는다. 기준 측정이 필요하면 측정 범위와 후속 결정 조건을 정하고, 결과에 따라 설계가 달라지는 불확실성을 숨기지 말라.

캐시의 오래된 값 허용, 과부하 시 제한·대기·거절, 대량 처리와 비용 상한의 충돌을 확인하라. 모든 작업에 부하 테스트나 새 성능 목표를 요구하지 않으며, 인터뷰 중 운영계 부하 실험을 실행하지 않는다.

## 보안·개인정보·악용 방지

입력·공개 표면·권한·민감 데이터의 변화에 맞춰 보호할 자산, 신뢰 경계와 행위자를 확인하라. 인증 여부뿐 아니라 객체·행위별 인가와 테넌트 간 격리가 어디서 보장되는지 조사한다.

관련 경로에 한해 입력 주입, 서버 측 외부 요청, 경로·파일 업로드, 출력·스크립트 처리, 세션·토큰·비밀, 재전송·반복 호출과 자원 고갈 같은 공격·오용 상황을 선택하라. 의존성·실행 환경 변경이 있으면 버전·설정의 근거도 확인한다. 전체 취약점 목록을 무조건 질문하지 않는다.

악용 시나리오의 입력·권한·영향, 기대 차단 동작과 검증 방법을 연결하라. 실제 근거로 확인한 취약점, 가능한 위협과 아직 조사하지 않은 영역을 구분하라. 미조사를 "취약점 없음"으로 보고하거나 인터뷰 완료를 보안 인증으로 표현하지 말라. 공격 실행·운영계 스캔·비밀 값 수집으로 범위를 넓히지 않는다.

## 관점 사이의 충돌 확인

각 관점이 따로 명확해도 함께 성립하지 않을 수 있다. 실제 선택이 충돌하는 경우에만 우선순위와 남은 비용을 합의하라.

- 감사·복구를 위한 장기 보관과 개인정보 최소 보관·파기
- 빠른 응답을 위한 캐시와 권한 회수·삭제의 즉시 반영
- 데이터 변경의 롤백과 이미 발생한 외부 부수효과
- 상세 관측 정보와 민감정보 노출·저장 비용
- 비동기 완료와 사용자에게 표시하는 성공·취소의 의미

결정 변경은 의존 관점의 상태·근거·검증 방법까지 갱신한다. 미충족 요구를 다른 관점의 장점으로 상쇄하지 않는다.
