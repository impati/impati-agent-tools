# 레포 기술 지침을 반영하는 시스템 관점 인터뷰와 검증 게이트

- **ID:** BL-0007
- **기록일:** 2026-09-24

## 배경

2026-09-24 `impati` 저장소의 BL-0074(택배사 기반 배송 진행) 작업에서는 제품 정책 인터뷰를 충분히 진행했지만, 구현 범위를 개별 기능에 가깝게 해석해 전체 시스템 경계와 실패 수렴 조건을 구현 전에 끝까지 검토하지 못했다.

실제 업체를 연결하지 않고 교체 가능한 로컬 구현을 둔다는 결정은 명확했다. 그러나 다음 두 캡슐화 경계는 별도 결정이었다.

1. 택배사 프로토콜의 멱등성·결과 조회·재시도·실패 수렴까지 모두 외부 구현이 책임진다고 가정한다.
2. 인증과 업체별 통신만 어댑터가 맡고, 업무 멱등 키·결과 불명 복구·로컬 상태와 외부 결과의 수렴은 애플리케이션이 명시적으로 구현한다.

이 구분을 인터뷰하지 않아 최초 구현은 외부 호출을 DB 트랜잭션 안에서 실행하고, 응답 유실 뒤 결과를 조회할 계약이나 영속 작업·재시도 경로가 없었다. 포장 완료와 취소가 경합하면 택배사에는 접수됐지만 로컬에는 운송장이 없거나, 택배사 취소는 성공했지만 주문 보상이 계속 실패할 수 있었다. 주문 쪽에서는 배송 사건 소비자가 읽은 오래된 주문 전체를 저장해 동시에 완료된 고객 취소를 되살릴 가능성도 있었다. 리뷰에서 문제를 발견했지만, 테스트는 정상 흐름과 단순 반복 호출 위주라 구현 단계에서 먼저 실패시키지 못했다.

근본 원인은 개별 실수 목록이 아니라 다음 세 가지다.

- `start-work` 인터뷰가 제품 정책과 기능 선택에는 강하지만 변경이 시스템 전체에 미치는 영향, 상태 소유자, 외부 부수효과의 실패 수렴을 완료 조건으로 요구하지 않는다.
- 프로젝트마다 다른 아키텍처 성격과 기술 기준을 하네스가 읽을 표준 진입점이 분명하지 않다. 공통 하네스에 특정 레포의 외부 연동 경계를 하드코딩하면 다른 레포에는 과하거나 틀릴 수 있다.
- 구현 완료를 검증하는 테스트 의무가 인터뷰에서 합의한 불변식·실패 시나리오와 연결되지 않는다. 커버리지 숫자를 높여도 응답 유실, 프로세스 종료, 동시성, 역순 사건 같은 핵심 실패 모드를 빠뜨릴 수 있다.

점검 항목을 계속 늘리는 방식도 해법이 아니다. 긴 체크리스트는 컨텍스트와 시간을 소비하고, 결국 읽기만 하고 실제로 사고하지 않는 형식적 절차가 된다. 사용자는 제품 의도와 책임 경계처럼 판단이 필요한 내용에 집중하고, 에이전트는 레포의 코드와 지침에서 기술 사실을 조사해 필요한 질문만 올려야 한다.

하네스와 레포의 책임은 다음처럼 나눈다.

| 위치 | 책임 |
| --- | --- |
| 공통 하네스 | 모든 기능 작업에서 시스템 관점을 적용하는 절차, 위험 신호에 따른 심화 검토, 인터뷰 결정과 테스트 의무의 추적, 리뷰의 독립 검증 |
| 대상 레포 | 아키텍처 성격, 상태와 트랜잭션의 소유 원칙, 외부 어댑터의 책임 범위, 동시성·재시도 관례, 표준 검증 명령 등 구체적인 기술 기준 |

## 확정된 방향

### 1. 레포 지침의 표준 진입점

- 하네스는 작업 시작 시 대상 저장소 루트에서 적용 가능한 `AGENTS.md`를 표준 진입점으로 읽는다.
- 하위 디렉터리에 더 구체적인 `AGENTS.md`가 있으면 기존 우선순위대로 함께 적용한다.
- `CLAUDE.md`처럼 특정 에이전트 전용 파일을 공통 정본으로 가정하지 않는다. 각 어댑터가 필요하면 `AGENTS.md`의 공통 지침을 해당 에이전트 형식으로 연결할 수 있다.
- 루트 `AGENTS.md`가 없다는 사실은 오류가 아니다. 그 경우 코드, ADR, 빌드 파일과 기존 관례를 조사하되 레포 고유 기준을 만들어내지 않는다.

### 2. 인터뷰에 시스템 관점을 추가

`start-work`는 기능 질문을 모두 마친 뒤 구현 승인 전에 한 번의 시스템 관점 검토를 수행한다. 고정된 세부 질문을 전부 사용자에게 묻는 방식이 아니라, 아래 관점을 내부적으로 검토하고 결과에 영향을 주는 결정만 질문한다.

- 변경이 통과하는 시스템·모듈·프로세스·데이터 저장소와 각 경계
- 상태와 사실의 정본, 쓰기 권한, 트랜잭션과 원자성의 경계
- 동기 호출, 비동기 사건, 외부 부수효과에서 성공·실패·결과 불명·중단 후 재개의 수렴 방식
- 중복, 순서 역전, 동시 실행, 재시도, 부분 성공, 데이터 불일치의 처리 주체
- 현재 구현에서 대역·어댑터·하위 시스템으로 캡슐화하는 범위와 애플리케이션이 직접 보장할 범위
- 변경을 소비하는 다른 서비스·배포 단위·운영 흐름과 관측·운영 확인 경로
- 기존 데이터나 배포 호환성이 실제 범위인지 여부

완료 조건은 “체크리스트 문장을 모두 읽었는가”가 아니라 “관련 관점마다 코드·레포 지침·사용자 결정 중 하나의 근거가 있고, 미결정 사항이 구현 결과를 바꾸지 않는가”다.

### 3. 위험 신호가 있을 때만 심화

평범한 단일 애그리거트 변경에 모든 분산 시스템 질문을 붙이지 않는다. 다음 신호가 있을 때 해당 관점을 확장한다.

- 원격 시스템이나 외부 업체에 상태를 바꾸는 호출
- 메시지, 웹훅, 스케줄러, 워커, Outbox/Inbox
- 둘 이상의 DB 트랜잭션이나 서비스가 하나의 업무 결과를 나눠 가짐
- 낙관적·비관적 잠금, 같은 자원에 대한 병렬 명령
- 마이그레이션, 기존 데이터 변환, 순차 배포 호환성
- 인증·서명·재전송 공격처럼 신뢰 경계를 넘는 입력

예를 들어 외부 부수효과가 있으면 최소한 업무 멱등 키의 소유자, 같은 키 재호출 계약, 결과 조회 가능성, 응답 유실 뒤 복구, 로컬 커밋과 외부 결과의 순서를 검토한다. 이것은 모든 인터뷰에 “외부 연동이 있습니까?”를 기계적으로 묻는 규칙이 아니라 코드에서 위험 신호를 발견했을 때 적용하는 사고 프레임이다.

### 4. 인터뷰 산출물과 테스트 의무를 연결

최종 구현 계획에는 장문의 체크리스트 대신 짧은 근거 표를 남긴다.

| 항목 | 기록 내용 |
| --- | --- |
| 영향 경계 | 바뀌는 시스템·소유 상태·호출자와 소비자 |
| 핵심 불변식 | 반드시 함께 성립하거나 절대 중복되면 안 되는 사실 |
| 실패 수렴 | 응답 유실·중단·경합 뒤 어떤 기록을 근거로 어디로 수렴하는지 |
| 테스트 의무 | 각 불변식과 실패 수렴을 어떤 자동 테스트가 깨뜨려 검증하는지 |
| 레포 근거 | 적용한 `AGENTS.md`, ADR, 기존 패턴과 검증 명령 |

테스트 완료 기준은 라인·브랜치 커버리지 수치가 아니다. 인터뷰에서 확인된 불변식과 실재 가능한 실패 시나리오가 자동 테스트에 대응해야 한다. 정상 흐름, 단순 재호출, 예외 한 번만으로 충분하다고 간주하지 않는다. 원격 변경이 있다면 응답 유실 후 조회 복구, 같은 멱등 키의 재사용, 로컬 커밋 실패, 프로세스 재시작을 검토하고 관련 있는 항목을 테스트한다. 동시 쓰기가 있다면 실제 저장소의 잠금·버전 조건을 통과하는 경합 테스트를 둔다.

### 5. 리뷰는 독립된 두 게이트로 동작

`rca-code-review`는 다음을 별도로 검사한다.

1. 구현이 인터뷰에서 확정한 정책, 책임 경계, 불변식과 테스트 의무를 지켰는가.
2. 인터뷰 자체가 레포 지침과 시스템 관점에서 빠뜨린 경계나 실패 모드가 없는가.

인터뷰 문서를 그대로 재확인하는 데 그치지 않는다. 커밋과 누적 diff에서 새로 드러난 호출·데이터 경계를 따라가며, 누락이 있으면 “테스트가 부족하다”보다 먼저 계약·소유권·인터페이스의 결함인지 판단한다. 테스트 대역이 우연히 중복을 막는 경우에도 실제 포트 계약에 멱등 키와 결과 조회가 없다면 인터페이스 결함으로 보고한다.

## 목표

`core/AGENTS.md`, `core/skills/start-work/SKILL.md`, `core/skills/rca-code-review/SKILL.md`와 지원 어댑터 배포본을 수정해 다음 상태를 만든다.

- 하네스가 대상 레포의 루트 및 적용 가능한 `AGENTS.md`를 먼저 찾아 레포 고유 기술 기준을 인터뷰·구현·리뷰에 사용한다.
- `start-work`가 기능 인터뷰 뒤 시스템 관점 검토를 수행하고, 관련 근거가 모두 채워져야 최종 구현 승인을 요청한다.
- 위험 신호가 없는 작업에는 추가 절차가 거의 없고, 위험 신호가 있는 작업만 필요한 질문과 검증이 확장된다.
- 사용자가 답해야 할 것은 제품 의도, 허용 가능한 실패 처리, 책임 경계처럼 선택이 필요한 사안이다. 코드로 확인 가능한 호출 관계나 레포 관례를 사용자에게 되묻지 않는다.
- 최종 계획의 핵심 불변식·실패 수렴마다 자동 테스트 의무가 대응하며, 커버리지 숫자를 완료 기준으로 사용하지 않는다.
- `rca-code-review`가 구현 준수와 인터뷰 완전성을 독립적으로 검사하고, 증상보다 계약과 구조의 근본 원인을 우선 보고한다.
- 공통 하네스에는 특정 업체·프로토콜·프레임워크를 하드코딩하지 않고 구체 기준은 대상 레포의 `AGENTS.md`에 남긴다.

## 완료 조건

- 샘플 작업 세 종류(단일 로컬 변경, 외부 부수효과가 있는 변경, 비동기 소비와 동시 쓰기가 있는 변경)에 대해 `start-work` 절차를 시뮬레이션했을 때 위험도에 맞는 검토만 활성화된다.
- 외부 호출을 DB 트랜잭션 안에서 실행하면서 결과 조회·영속 복구가 없는 예제를 최종 계획 전에 차단한다.
- 대역 구현의 내부 맵만 멱등하고 포트 계약에는 멱등 키가 없는 예제를 인터페이스 결함으로 식별한다.
- 비동기 소비자가 낡은 전체 행을 저장해 동시 변경을 덮는 예제를 테스트 의무와 리뷰 발견 사항으로 식별한다.
- 정상 흐름 테스트만 있고 응답 유실·부분 성공·경합 테스트가 없는 위험 작업은 구현 완료로 판정하지 않는다.
- 같은 내용을 긴 범용 체크리스트로 반복하지 않고 근거 표와 위험 신호 기반 확장으로 표현한다.
- Codex와 지원 중인 다른 에이전트 어댑터에 배포된 지침이 공통 정본과 일치한다.
- 하네스 자체 검증 명령과 어댑터 동기화 검사가 통과한다.
