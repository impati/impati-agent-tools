# 결정 전에 문제 상황을 처음 보는 사람 기준으로 설명하는 스킬

- **ID:** BL-0005
- **기록일:** 2026-08-23

## 배경

2026-08-23, `impati` 저장소에서 BL-0002(이메일 확인 토큰이 URL 쿼리에 담겨 유출되는 문제) 작업을 시작하면서 `start-work` 인터뷰에 들어갔다. 방안 A/B/C와 장단점, 추천안을 제시했으나 사용자는 "이 작업에 대한 문제 상황을 이해하지 못했다, 처음 마주한 사람에게 자세히 설명해달라"고 요청했다.

즉 `start-work`는 "선택지 2~3개와 장단점, 추천안"을 요구하지만, **그 선택지를 이해하는 데 필요한 배경을 먼저 세우는 단계가 없다.** 사용자가 배경을 모르면 선택지 비교 자체가 성립하지 않는다.

방치할 때의 비용:

- 배경 없이 제시된 선택지는 사용자가 판단할 수 없어 인터뷰가 한 라운드 더 돈다. 이번에 실제로 발생했다.
- 더 나쁜 경우, 사용자가 이해하지 못한 채 추천안을 승인한다. 그러면 `start-work`의 "사용자 의도 파악"이 형식만 남는다.
- 같은 질문을 반복하게 된다. 배경을 제대로 세우면 "모르는 것을 새로 묻기는 해도 같은 것을 두 번 묻지는 않는다"는 것이 사용자 피드백이다.

이 문제를 항상 로드되는 `CLAUDE.md` 규칙으로 넣지 않는 이유:

- 설명 구조를 상시 규칙으로 넣으면 매 세션 컨텍스트를 소비한다. 적용 프로젝트(`impati`)의 `CLAUDE.md`는 "짧게 유지한다"를 명시하고 있다.
- 더 중요한 이유는 항상 길게 설명하면 긴 설명이 신호가 아니라 기본값이 되는 것이다. 사소한 질문에도 배경 세 단락이 붙으면 정작 필요할 때 눈에 띄지 않는다.
- 스킬은 호출될 때만 로드되므로 평소 비용이 0이다.

관측 횟수는 1회다(2026-08-23, `impati` BL-0002).

## 목표

가칭 `explain-problem` 스킬을 만들어, 결정 전에 문제 상황을 그 문제를 처음 보는 사람 기준으로 설명하는 절차를 갖는다. `core` 스킬로 두고 `start-work` 인터뷰 단계에서 참조할 수 있게 한다.

스킬에 담을 설명 구조는 이번에 실제로 효과가 있었던 순서를 그대로 템플릿화한다.

1. **기능이 무엇을 하는지부터.** 실제 코드 인용과 `파일:라인` 링크로 설명한다. 문제가 아니라 정상 흐름부터 시작한다.
2. **근본 원인을 한 문장으로.** "URL은 비밀을 담는 그릇이 아니다"처럼. 증상을 나열하기 전에 원인을 박는다.
3. **경로와 실패 모드를 표로 분리.** 각각 독립적으로 적는다. 뭉뚱그리면 무엇이 무엇을 막는지 판단할 수 없다.
4. **지금 진짜 깨진 것과 기본값이 가려주고 있는 것을 구분.** 가장 중요한 항목이다. 이번에 이것을 구분했기 때문에 사용자가 백로그 원안과 다른 방안을 고를 수 있었다. 이 구분이 없으면 "실재하는 경로"와 "지금 새는 경로"가 섞여 우선순위가 뒤집힌다.
5. **피해 크기를 과장 없이.** "지금은 제한적이다"를 먼저 인정하고, 그럼에도 고쳐야 하는 이유를 따로 댄다. 부풀리면 신뢰를 잃는다.
6. **예상 반문에 미리 답한다.** "일회용 토큰인데 이미 소진된 것 아닌가?" 같은 반문에 표로 반례를 보인다.
7. **방안별로 "막는 것 / 못 막는 것" 표.** 그리고 각 방안의 비용과 부작용.
8. **추천안과 이유.** 하나를 고르고 왜인지 댄다.

발동 조건:

- 사용자가 "자세히 설명해줘", "처음 보는 사람 기준으로", "이해가 안 된다", "이게 왜 문제야"라고 할 때.
- `start-work` 인터뷰에서 선택지를 내기 전, 사용자가 문제 배경을 모를 것으로 보일 때.

해결 판정(O/X):

- `start-work` 인터뷰에서 사용자가 "문제를 이해하지 못했다"며 재설명을 요청하는 일이 없다: O/X
- 스킬을 적용한 설명에 위 8단계가 모두 포함된다: O/X

산출물은 `core/skills`와 어댑터 배포본에 같은 내용으로 존재해야 한다.
