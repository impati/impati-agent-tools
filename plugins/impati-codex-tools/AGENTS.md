# 작업 원칙

이 저장소에서 작업하는 모든 에이전트는 다음 원칙을 우선한다.

## 제1원칙: 사용자의 의도를 완전히 파악한다

- 작업 전에 사용자의 목표, 요청 범위, 제약 조건, 완료 기준을 파악한다.
- 구현이나 변경에 여러 유효한 방법이 있으면 2~3개의 선택지와 핵심 장단점을 제시한다.
- 추천 방향과 추천 이유를 함께 설명하고, 사용자가 방향을 확정한 뒤 작업한다.
- 사용자가 이미 방법을 명확히 지정했거나 즉시 실행을 요청했다면 같은 결정을 다시 묻지 않는다.
- 선택지가 실질적으로 하나뿐이라면 억지로 대안을 만들지 말고 그 이유를 짧게 설명한다.

## 규칙 우선순위

- 이 하네스의 규칙은 여러 프로젝트에서 사용할 공통 기본값이다.
- 하네스 규칙과 실제 작업 대상 프로젝트의 로컬 규칙이 충돌하면 더 구체적인 로컬 프로젝트 규칙을 우선한다.
- 로컬 규칙에는 대상 프로젝트의 `AGENTS.md`, 설정, 문서화된 관례, 도구 체인, 빌드·테스트·검증 명령이 포함된다.
- 시스템·개발자·안전 정책과 현재 사용자의 명시적 요청은 로컬 규칙으로 덮어쓰지 않는다.
- 어느 규칙이 더 구체적이거나 충돌하는지 불명확하면 제1원칙에 따라 사용자에게 확인한다.

## 요청 범위를 지킨다

- 사용자가 요청한 결과를 만드는 데 필요한 작업만 수행한다.
- 관련 있어 보이더라도 요청하지 않은 리팩터링, 기능 추가, 설정 변경, 파일 수정은 하지 않는다.
- 추가 작업이 유용해 보이면 실행하지 말고 선택 사항으로 제안한다.
- 요청 범위를 넘어서는 권한, 외부 시스템 변경 또는 파괴적 작업이 필요하면 먼저 사용자의 승인을 받는다.

## 모호함을 처리한다

- 모호함이 결과, 범위, 데이터 또는 되돌리기 어려운 결정에 영향을 주면 작업 전에 질문한다.
- 안전하게 되돌릴 수 있는 사소한 세부사항만 합리적으로 가정할 수 있으며, 그 가정은 사용자에게 명시한다.
- 질문할 때는 무엇이 모호한지, 가능한 방향이 무엇인지, 각 방향이 결과에 어떤 차이를 만드는지 설명한다.

## 작업 진행과 완료

- 방향이 확정되기 전에는 읽기와 진단 등 안전한 확인만 수행한다.
- 비즈니스 로직, 사용자 동작, API, 데이터, 아키텍처, 보안, 성능 또는 런타임 동작에 영향을 주는 코드 작업을 시작하기 전에 `start-work` 스킬을 사용한다.
- 모든 기능 코드 작업은 `BL-NNNN` 백로그 ID와 연결한다. ID가 없으면 구현 전에 `capture-backlog`로 항목을 먼저 생성한다.
- 백로그 기반 기능 브랜치는 로컬 규칙이 없을 때 `feature/bl-NNNN-kebab-case-title` 형식을 사용한다.
- 백로그 기반 커밋은 로컬 규칙이 없을 때 `<type>(bl-NNNN): <한국어 요약>` 형식을 사용한다.
- 문서, 백로그, 변경 로그, 포맷팅, 주석, 오탈자, 스킬 또는 작업 규칙만 변경하는 작업에는 `start-work`를 자동 적용하지 않는다.
- 현재 대화에서 `start-work`와 동등한 수준의 인터뷰와 최종 승인이 이미 끝났다면 같은 질문을 반복하지 않고 그 합의를 사용한다.
- 사용자가 `작업 시작`, `인터뷰`, `의도 파악` 또는 `$start-work`를 요청하면 누락된 `start-work` 절차를 즉시 적용한다.
- 기능 영향 여부가 불명확하면 제1원칙에 따라 사용자에게 확인한다.
- 이 하네스 저장소 자체의 변경에는 ADR을 작성하지 않는다. 과거와 현재의 변경 의도는 `CHANGELOG.md`로 관리한다.
- 작업 중 발견한 별도 문제는 임의로 수정하지 않고 보고한다.
- 저장소를 변경한 작업은 완료 전에 `CHANGELOG.md` 최상단에 기록한다.
- 개별 백로그 항목 추가는 `CHANGELOG.md` 기록 대상에서 제외한다.
- 변경 기록은 날짜와 제목, 변경 의도, 핵심 변경, 중요한 결정만 간결하게 적는다.
- 기존 기록과 같은 내용을 반복하거나 구현 세부사항을 길게 나열하지 않는다.
- `CHANGELOG.md` 분리는 메이저 변경이 생기거나 문서가 지나치게 길어진 뒤 사용자와 방향을 확정하여 진행한다.
- 완료 시 변경한 내용, 검증 결과, 남은 제약이나 위험을 간결하게 알린다.

## 저장소 스킬

- 기능 동작에 영향을 주는 코드 작업 전에 사용자 의도와 주요 결정을 인터뷰할 때 `start-work` 스킬을 사용한다.
- `start-work`의 세부 절차는 `.agents/skills/start-work/SKILL.md`를 따른다.
- 지금 구현하지 않을 문제나 작업 후보를 `docs/backlog`에 기록할 때 `capture-backlog` 스킬을 사용한다.
- `capture-backlog`의 세부 절차는 `.agents/skills/capture-backlog/SKILL.md`를 따른다.
- 사용자가 `$rca-code-review` 또는 코드 리뷰를 명시적으로 요청하면 백로그 브랜치를 RCA 다관점으로 리뷰하고 채팅에 보고한다.
- `rca-code-review`의 세부 절차는 `.agents/skills/rca-code-review/SKILL.md`를 따른다. 작업 완료 후 자동 실행하지 않는다.
- 사용자가 코드 작업, 트러블슈팅, 구현 결정, 아키텍처, 동시성, 테스트 또는 교훈을 한국어 기술 문서로 정리해 달라고 하면 `engineering-writeup` 스킬을 사용한다.
- 스킬의 세부 절차는 `.agents/skills/engineering-writeup/SKILL.md`를 따른다.
- 사용자가 플러그인 버전 릴리스 또는 원격에 반영된 최신 플러그인의 로컬 설치를 요청하면 `release-plugin` 스킬을 사용한다.
- `release-plugin`의 세부 절차는 `.agents/skills/release-plugin/SKILL.md`를 따른다.

## 플러그인 버전

- `plugins/impati-codex-tools/.codex-plugin/plugin.json`의 `version`을 플러그인 버전의 단일 기준으로 사용한다.
- 플러그인 배포물에 변경이 생기면 SemVer 영향도를 판단하여 같은 변경에서 버전을 갱신한다.
- 호환되지 않는 스킬·규칙 계약 변경은 MAJOR, 하위 호환 기능 추가는 MINOR, 호환 가능한 수정은 PATCH로 올린다.
- 플러그인 밖의 문서나 개발 보조 파일만 변경되었다면 버전을 올리지 않는다.
- 버전 변경은 `CHANGELOG.md` 최상단에 해당 버전의 의도와 핵심 변경을 함께 기록한다.
- tag, push와 GitHub release는 사용자의 명시적 요청 없이 자동 수행하지 않는다.
